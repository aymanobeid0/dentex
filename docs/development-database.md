## فحص المستخدم المحلي قبل PR

توجيه المستخدم الدائم المعتمد في 2026-11-03: في نهاية تنفيذ كل تذكرة وبعد تحقق الوكيل، شغّل التطبيق محليًا على قاعدة التطوير الدائمة `dentex_dev` ليختبر المستخدم التغييرات قبل فتح PR. اترك السيرفر وقاعدة البيانات يعملان بعد التسليم وبين التذاكر؛ لا توقفهما ضمن تنظيف أدوات QA. إذا كانا يعملان بالفعل، استخدم التشغيل القائم بعد التحقق من أنه يعرض أحدث الكود ويتصل بقاعدة التطوير الصحيحة. عند تعذر التشغيل، سجّل العائق صراحة ولا تدّع الجاهزية.

متطلب التهيئة الأولى التالي نُفذ بالفعل: سُئل المستخدم عن الأسماء وأسماء الدخول والبريد حيث يلزم، وأدخل كلمات المرور محليًا بصورة مخفية للهويات الأربع التالية. احفظ الحسابات القائمة الآن ولا تعِد التهيئة:

- مدير عام للتطبيق، في حساب مدير البرنامج المستقل المعتمد.
- مدير عيادة مرتبط بالعيادة ذات الرمز `2000`.
- طبيب في العيادة نفسها، بدور الطبيب المعتمد `dentist`.
- موظف في العيادة نفسها، بدور الموظف/الاستقبال المعتمد `receptionist`.

المقصود أربعة حسابات بهويات وصلاحيات النظام الحالية، وليس إضافة أربعة أدوار جديدة أو تغيير المعمارية. استُبدل الإعداد المحلي الملغى وأُنشئت عيادة الفحص بالرمز `2000` والحسابات وفق إجابات المستخدم في قاعدة التطوير الجديدة بتاريخ 2026-11-03؛ لا تعِد العملية. لا تنفذ السكربت القديم ولا تعِد استخدام بيانات دخوله تلقائيًا. بعد اكتمال التهيئة الجديدة والتحقق منها، أعد استخدام العيادة والحسابات نفسها دائمًا في التذاكر التالية، دون تكرار التهيئة أو تغيير كلمات المرور والصلاحيات تلقائيًا. إذا كانت الإجابات لم تصل أو توقفت التهيئة، سجّلها كتهيئة غير مكتملة؛ لا تدّع الجاهزية ولا تفتح PR قبل فحص المستخدم.

تبقى هذه العيادة والحسابات وبيانات فحص المستخدم محفوظة في قاعدة التطوير وvolume نفسها عبر التذاكر وإعادة التشغيل. لا reset أو حذف volume أو تنظيف لهذه البيانات، ولا تشغيل اختبارات آلية عليها؛ تستمر الاختبارات الآلية على `dentex_test` المعزولة. تبقى قاعدة التطوير شغالة بين التذاكر ما دام الجهاز وDocker يعملان؛ بعد إعادة تشغيلهما أعد تشغيل البيئة مع التخزين نفسه.

عند التسليم، أعط المستخدم الرابط المحلي ورمز العيادة وأسماء الحسابات المتاحة دون كلمات مرور في الوثائق أو المحادثة، وانتظر مراجعته قبل فتح PR. يجب أن يتضمن كل handoff إحالة إلى هذا القسم وحالة التطبيق وقاعدة البيانات والتهيئة الأولى ومراجعة المستخدم، مع تمييز المطلوب عن المنفذ فعليًا. الإذن السابق بالرفع لا يلغي ترتيب الفحص المحلي قبل PR للتذاكر اللاحقة.

حالة تنفيذ هذا التوجيه: اكتملت التهيئة الجديدة والتحقق كما في بداية الدليل؛ الإعداد1234 تاريخي ملغى وليس إعدادًا يُعاد اعتماده. `scripts/seed-local.mjs` سكربت قديم خاص بعيادة `1234` وحسابين، وأُلغي اعتماده لهذا المسار؛ وجوده في المستودع لا يسمح باستخدامه بدل التهيئة الجديدة.

## التشغيل

- تشغيل قاعدة البيانات: `docker compose up -d --wait`.
- الإيقاف مع الحفاظ على البيانات: `docker compose stop`.
- تشغيل التطبيق محليًا بعد تثبيت الاعتماديات: `npm run dev`، ثم افتح `http://127.0.0.1:5151`. بطلب المستخدم في2026-11-04 نُقل المنفذ إلى5151؛ API المحلي لهذه النسخة على5152 (`PORT` في.env)، ويقرأ Vite المنفذ نفسه لوكيل `/api`. يستخدم Vite strictPort حتى لا ينتقل بصمت إلى منفذ مختلف.
- استخدم العنوان السابق كما هو: إعداد `APP_ORIGIN` المحلي الحالي يعتمد `http://127.0.0.1:5151`. مصدر آخر يُرفض بـ403 `untrusted_origin` قبل فحص الحساب. مراجع5173/3000 في أدلة التحقق السابقة تاريخية. وُجدت نسخة أخرى تعمل من مجلد dentex-review على5173/3000؛ لا توقفها أو تعتمدها لفحص D:/dentex. لا تعالج اختلاف المصدر بإعادة إنشاء القاعدة أو تغيير كلمات المرور تلقائيًا.
- البيانات محفوظة في volume مستقل. لا تحذف volume لإعادة التشغيل أو التجربة.
- ملف `.env` يحتوي بيانات الاتصال المحلية ومستثنى من Git؛ لا تُطبع محتوياته أو تُنقل إلى المواصفات والتذاكر.
- كلمات مرور الحسابات لا تُحفظ في ملفات المشروع كنص صريح. سكربت `scripts/seed-local.mjs` ملغى الاعتماد ولا يُستخدم لتهيئة البيئة الجديدة.

## التحقق من نسخة التطبيق

ابدأ بـ`npm run check:dev` علىWindows من جذر المشروع. يفحص الإعدادات ومالكي المنفذين وحالة التخزين واتصالًا للقراءة فقط بـdentex_dev وHTTP وقبول المصدر بطلب دخول فارغ بلا بيانات اعتماد. النجاح يثبت جاهزية التشغيل المحلي فقط؛ تحقق المتصفح والدخول الفعلي منفصلان. عند تعذر صلاحية فحص العمليات أوDocker يفشل الأمر بدل إعلان الجاهزية، ولا يشغّل أو يوقف خدمات ولا يعدّل بيانات أو إعدادات.

استخدم `npm run check:dev -- --json` للمخرجات الآلية: كود الخروج1 يعني فشلًا، واسم الفحص الفاشل يحدد المرحلة دون طباعة أسرار أو سطر تشغيل العمليات. `--config-only` يعمل دون الوصول للعمليات أوDocker أوHTTP أوالقاعدة، ويعيد دائمًا `ready:false` حتى مع صحة الإعدادات. فحص العمليات الكامل مخصص لـWindows؛ لا تشغله فيCI بوصفه فحص التطبيق المبني.

نفّذ هذه الخطوات قبل اعتماد جاهزية بيئة الفحص، وعند تعذر الدخول أو وجود نسخة أخرى من المشروع:

1. طابق المنفذ مع ملف `vite.config.ts`، ومصدر المتصفح مع `APP_ORIGIN`، ومنفذ API مع `PORT` في ملف البيئة المحلي. افحص هذه القيم وحدها؛ احتفظ بـDATABASE_URL وJWT_SECRET وكلمات المرور خارج المخرجات.
2. حدد مالك منفذي الواجهة والخادم، وتحقق من أن مسارات تشغيلهما تخص جذر هذا checkout. على Windows استخدم `Get-NetTCPConnection` ثم `Get-CimInstance Win32_Process` للتحقق محليًا من مسار الأمر ومعرّف العملية. سجّل المنفذ والمسار المتوقع ونتيجة المطابقة فقط. استجابة200 أو عنوانDentex لا يثبتان أن العملية تخص هذا المشروع.
3. تحقق من مصدر إعداد الاتصال: قاعدة `dentex_dev` على55460، والحاوية `dentex-database-1` صحية، والتخزين `dentex_database_data`. عند الاشتباه، افحص وجود العيادة والحسابات وحالتها للقراءة فقط؛ ثبوت وجود الحساب لا يثبت صحة كلمة المرور المدخلة.
4. افحص الواجهة و`/api/auth/me` عبر وكيل Vite وعنوان API.401 دونCookie نتيجة متوقعة تثبت وصول الطلب فقط. طابق المصدر قبل تشخيص بيانات الاعتماد؛403/untrusted_origin ليس خطأ كلمة مرور، و401/invalid_credentials يحتاج فحص الحساب/العيادة والمدخلات الفعلية دون تخمين كلمات المرور.
5. سجّل نتيجة المتصفح منفصلة عنHTTP: ظهور شاشة الدخول، قبول المصدر، نجاح دخول فعلي، وفحص المستخدم حالات مختلفة. عند تعذر وصول المتصفح، سجل القيد كما هو؛ وعند طلبPR صريح سجل الإذن دون تحويله إلى إقرار بفحص يدوي.

إذا شغل المنفذَ checkout آخر، احتفظ بعملياته وبياناته وحدد منافذ مستقلة للنسخة الحالية كما حدث مع5151/5152. شغّل `npm run dev` من جذر المشروع حتى يجد npm الأدوات المحلية. عند التشغيل في الخلفية علىWindows استخدم نافذة مخفية وسجل stdout/stderr خارجGit، واحتفظ بمسار السجل ومعرّفات العمليات في التسليم دون أسرار. اقرأ السجل المختصر عند فشل التشغيل قبل تكرار المحاولة.

اكتمال الخطوة: مسار العمليتين والمصدر وإعداد قاعدة البيانات معلومة، وHTTP والمتصفح موثقان كلٌّ بنتيجته الفعلية. آخر مثال تطبيقي في [تحقق03](../.scratch/frontend-state-migration/03-verification.md#متابعة-تشغيل-المستخدم--نقل-المنافذ).

## ملاحظات التنفيذ والمحافظة على البيانات

1. اقرأ AGENTS.md والمواصفة المحلية وعقد الشاشات، والتزم بالتصميم المعتمد في login-preview.html.
2. تاريخيًا، اعتُمد الترحيل `20261101000000_baseline` للقاعدة القديمة بعد المقارنة ثم طُبق `20261101010000_role_permissions`. عند التهيئة الجديدة طبّق كل الترحيلات على القاعدة الجديدة بأمر `npm run db:deploy`؛ بعد اعتماد الإعداد الجديد احتفظ ببياناته وطبّق الترحيلات اللاحقة دون reset.
3. تنسيق تجزئة كلمات المرور: `scrypt$N$r$p$saltHex$keyHex`، حيث N=32768 وr=8 وp=1 وطول المفتاح 64 بايت. ملح scrypt المستخدم هو النص السداسي نفسه (UTF-8)، وليس تحويله إلى بايتات؛ طابقه عند التحقق. استعمل مقارنة ثابتة الزمن.
4. مدير البرنامج في جدول مستقل، ومدير العيادة مربوط بدور admin. طُبقت الصلاحيات المبدئية لدوري dentist وreceptionist؛ يحتفظ دور admin بكامل صلاحيات العيادة في التطبيق.
5. اختبارات التطبيق تستخدم قاعدة `dentex_test` منفصلة وبيانات وهمية؛ لا توجه اختباراتها إلى قاعدة التطوير. إعدادات JWT ومصدر الواجهة محفوظة في `.env` المحلي المستثنى من Git.
6. إعداد قاعدة التطوير لا يعني إغلاق تذاكر التطبيق؛ تُقيّم كل تذكرة وفق تنفيذها واختباراتها والتحقق من واجهتها.

## قاعدة الاختبار

الاختبارات الكاملة تحتاج PostgreSQL محلية بقاعدة مستقلة اسمها `dentex_test`. استخدم بيانات اعتماد محلية مخولة بإنشائها أو أنشئها مسبقًا؛ لا تستخدم `dentex_dev` ولا بيانات الإنتاج. ملف الاتصال المحلي مستثنى من Git ولا تُطبع محتوياته.

### قاعدة اختبار جديدة

من جذر المشروع، بعد تثبيت الاعتماديات وتوليد Prisma Client:

```sh
node scripts/migrate-test.mjs
node scripts/test-local.mjs
```

يمكن تمرير مسار ملف البيئة المحلي كوسيط للأمرين. يقرآن DATABASE_URL منه، ويرفضان المضيف البعيد، ويستبدلان اسم القاعدة بـ`dentex_test`. سكربت الترحيل ينفذ `prisma migrate deploy` فقط؛ لا يحذف بيانات ولا يسجل ترحيلًا على أنه مطبق دون تنفيذه. لا يكفي `database/bootstrap.sql` لتهيئة المخطط الحالي، إذ لا يحتوي جدول المرضى.

### القاعدة القديمة المستخدمة محليًا

قاعدة dentex_test القديمة على منفذ55460 بلا migration ledger؛ لا توجه إليها تحققًا آليًا يفترض قاعدة جديدة، ولا تستخدم reset أو resolve افتراضيًا. تحقق03 شغّل167 اختبارًا على حاوية مؤقتة منفصلة وdentex_test جديدة بترحيلاتها الأربعة، ثم حذف حاويتها وحدها؛ بيئةdev والقاعدة القديمة حُفظتا. التفاصيل في [دليل03](../.scratch/frontend-state-migration/03-verification.md). أعداد الاختبارات في الأدلة السابقة تخص أوقاتها.

### قاعدة اختبار قديمة منشأة بـbootstrap

إذا ظهر `P3005` لأن القاعدة غير فارغة وبلا سجل ترحيلات، أوقف مسار التهيئة وافحص مخطط `dentex_test` وقيوده مقابل ملفات `prisma/migrations/`؛ لا تستخدم reset أو `db push` لتجاوز المشكلة.

في اتصال مضبوط صراحة على `dentex_test`، سجّل عبر `prisma migrate resolve --applied <migration-name>` كل ترحيل أثبتت المقارنة أنه مطبق بالفعل، ثم شغّل `node scripts/migrate-test.mjs` لتطبيق الباقي. لا تسجل ترحيل المرضى لمجرد وجود الجداول القديمة، ولا تفترض أن ترحيل الصلاحيات مطبق دون مقارنة جداوله ومنحه. عند تعذر إثبات التطابق، استخدم بيئة PostgreSQL محلية منفصلة بقاعدة `dentex_test` جديدة مع الحفاظ على القاعدة القديمة.

قاعدة الاختبار المستخدمة في تنفيذ التذكرة 01 كانت منشأة بـbootstrap وبلا سجل Prisma؛ أضيف إليها SQL ترحيل المرضى مباشرة للتحقق. لذلك لا يُفترض أن سجل ترحيلاتها مكتمل؛ يظل مسار المقارنة أعلاه لازمًا قبل تحويلها إلى إدارة Prisma migrations.

### CI

تعريف `.github/workflows/ci.yml` يجهز خدمة PostgreSQL مستقلة بقاعدة `dentex_test` فارغة، ويطبق الترحيلات كاملة، ثم يشغل فحص المعمارية والبناء والاختبارات. يتحقق `scripts/check-test-report.mjs` من عدم وجود اختبارات فاشلة أو متخطاة أو todo. لا يتصل هذا التعريف بقاعدة التطوير. التعريف مرفوع ضمن طلب السحب #2؛ تُراجع نتيجة التشغيل الفعلية من Checks. لم تُضبط حماية الفروع ضمن هذه المهمة.
