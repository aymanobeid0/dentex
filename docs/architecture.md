# معمارية الخادم المعتمدة

اعتمد المستخدم القرارات التالية في 2026-11-03. اكتمل ترحيل الحسابات إلى هذه المعمارية محليًا؛ أدلة التنفيذ والتحقق وحالة Git في `.scratch/architecture/handoff.md`. تستكمل قرار التطبيق الموحد مع PostgreSQL ولا تغير سلوك المنتج المعتمد.

## سلطة التغيير — إلزامية

المستخدم وحده يجيز تغيير المعمارية. ينطبق ذلك على أي تغيير ولو صغيرًا في تقسيم الموديولات أو هيكل ملفاتها المعتمد أو مسؤوليات الطبقات أو Interface بين الموديولات أو ملكية البيانات والمعاملات أو نهج التحقق والأخطاء أو قواعد الفحص. يشمل الاستثناءات المؤقتة وتجاوز القواعد وتغيير الوثائق المعمارية ذاتها.

عند اقتراح تغيير:

1. حدد القاعدة الحالية والتغيير المحدد وسببه والملفات أو العقود المتأثرة والمخاطر والبديل الموافق للمعمارية.
2. اطلب موافقة صريحة من المستخدم على ذلك التغيير، وأوقف الجزء المعتمد عليه حتى وصولها. يمكن متابعة أعمال مستقلة ملتزمة بالقرارات القائمة.
3. لا تستنتج الموافقة من الصمت أو ضيق الوقت أو نجاح الاختبارات أو طلب تنفيذ ميزة أو رأي وكيل آخر. الموافقة على تغيير محدد لا تشمل تغييرات أخرى.
4. بعد الموافقة، سجل نص القرار أو معناه الدقيق وتاريخه ونطاقه في وثيقة القرار المناسبة، وحدّث المرجع المعماري قبل تطبيقه.

تنفيذ العمليات داخل المعمارية المعتمدة ضمن مهمة مأذونة لا يحتاج إذنًا متكررًا؛ إضافة موديول وفق القالب لميزة مأذونة ليست تغييرًا للمعمارية. أما الاختيار المعماري غير المحسوم أو الاستثناء فيُعرض على المستخدم قبل تنفيذه. لا يجوز تعديل هذه القاعدة أو اختبارات المعمارية لتسهيل تمرير مخالفة.

## تنظيم الموديولات

Module لكل ميزة مترابطة، مثل المرضى والموظفين، وليس لكل عملية منفردة. داخل مجلد الميزة:

```text
patients/
  patients.routes.ts
  patients.controller.ts
  patients.service.ts
  patients.repository.ts
  patients.schemas.ts
  patients.dto.ts
  patients.errors.ts
  index.ts
```

- route يربط المسارات بالمتحكم والتحقق من الجلسة والصلاحية.
- controller يعالج HTTP ويستدعي التحقق من المدخلات ويحوّل النتائج الناجحة إلى ردود؛ تمر الأخطاء إلى المعالج العام.
- service يملك قواعد العمل وتنسيق العمليات ونطاق المعاملة؛ يبقى مستقلًا عن Express وPrisma.
- repository ينفذ استعلامات التخزين، بما فيها الأقفال والعمليات الذرية اللازمة لحفظ الضمانات.
- schemas يحتوي مخططات Zod للتحقق الفعلي من المدخلات وتوحيد صيغها. تُستنتج أنواع المدخلات منها بدل تكرارها يدويًا؛ dto يحدد عقود البيانات المسموح تبادلها.
- errors يحتوي أخطاء الميزة المعروفة وفق شكل أخطاء مشترك.
- index يعلن Interface الموديول المسموح للمستدعين استخدامها؛ لا يعيد تصدير جميع الملفات الداخلية.

يبقى إعداد التطبيق وتجميع الاعتماديات وربط الموديولات خارج قواعد العمل. البنية السابقة تخص الخادم؛ لا تُفرض طبقات repository/controller على React.

## التواصل وملكية البيانات

التواصل بين الموديولات عبر Interface المعلنة فقط. لا تستورد الموديولات repositories بعضها أو ملفاتها الداخلية، ولا تصل مباشرة إلى جداول ميزة أخرى. تنقل العقود بيانات واضحة وأخطاء معروفة دون أنواع Prisma أو Express. يجب أن يبقى رسم الاعتماديات غير دائري.

## المعاملات

service يطلب المعاملة ويحدد الخطوات التي يجب أن تنجح معًا. TransactionManager ينفذها عبر Prisma ويقدم repositories مرتبطة بالمعاملة نفسها. لا يُمرر Prisma أو TransactionClient إلى service؛ ولا يُسمح أن تنفذ خطوة من العملية بمعاملة منفصلة دون قصد.

عندما تمتد العملية عبر موديولات، تظل الاستدعاءات عبر Interface المعلنة؛ لا يتيح TransactionManager repositories موديول آخر للمستدعي. اعتمد المستخدم واجهات عمليات الموديولات المعلنة المرتبطة جميعًا بمعاملة واحدة: تقدم أداة المعاملات هذه الواجهات للعملية وتخفي تفاصيل Prisma. يُتحقق من الذرية باختبار تراجع يشمل الموديولات المشاركة. أي تغيير عن هذا التصميم يحتاج موافقته المسبقة.

## التحقق والأخطاء

Zod يتحقق من شكل المدخلات عند HTTP؛ service يفرض قواعد العمل؛ قيود التخزين تحمي التفرد والتزامن. تحقق الصلاحية في route لا يلغي إعادة التحقق داخل العمليات الحساسة عند الحاجة لمنع السباقات القائمة في التطبيق.

أخطاء كل موديول تتبع عقدًا موحدًا، والأخطاء المشتركة للدخول والصلاحيات منفصلة. المعالج المركزي يحوّل الأخطاء المعروفة إلى رموز HTTP واستجابات متسقة، ويحوّل الأخطاء غير المتوقعة إلى 500 دون كشف تفاصيل حساسة، مع تسجيلها داخليًا. يظل service مستقلًا عن HTTP. الواجهة تختار الرسالة بحسب كود الخطأ واللغة.

أثناء إعادة التنظيم تُحفظ رموز الأخطاء وصيغ الاستجابات الحالية؛ إدخال المعالج المركزي لا يبرر كسر عقد الواجهة أو تغيير الرسائل.

## الفحص ومعيار الإتمام

اعتمد المستخدم ESLint وفحص الاعتماديات ضمن أمر check:architecture المستهدف. يجب أن يكشف استخدام Prisma خارج الوصول للبيانات وتجهيز التطبيق، واستيراد الملفات الداخلية بين الموديولات، واعتماد قواعد العمل على HTTP، والدورات. يُثبت الفحص بأمثلة مخالفة وأخرى سليمة؛ المراجعة البشرية تكمل ما لا يمكنه كشفه من توزيع المسؤوليات.

تُنجز إعادة تنظيم المصادقة والعيادات والموظفين والأدوار والصلاحيات والحساب الشخصي قبل تنفيذ المرضى. تُحفظ العقود والسلوك والصلاحيات وعزل العيادات والمعاملات. اختبارات السلوك الموجودة والبناء وفحص المعمارية معايير لازمة للإتمام؛ لا يكفي وجود الملفات بالأسماء المطلوبة.

قبل إغلاق أي مهمة، يراجع الوكيل الالتزام بمسؤوليات الطبقات والاستيرادات والمعاملات والتحقق والأخطاء، ويسجل نتائج الفحوص والقيود. يمنع تعطيل قاعدة أو إضافة تجاهل أو استثناء لترحيل الكود القديم دون موافقة المستخدم المحددة على نطاقه وشرط إزالته. نجاح اختبارات السلوك وحده لا يثبت الالتزام المعماري.

حالة التنفيذ في 2026-11-03: يمر أمر `check:architecture` باستخدام ESLint وdependency-cruiser بعد إزالة الملفات القديمة، مع اختبارات أمثلة سليمة ومخالفة ودون استثناءات للترحيل. نُفذت مراجعة ملكية الجداول وتوزيع المسؤوليات واختبار تراجع الواجهات الفعلية المرتبطة بمعاملة واحدة. تظل هذه المراجعة مطلوبة للتغييرات التالية ولا يغني عنها الفحص الآلي.
