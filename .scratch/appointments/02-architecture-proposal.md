# المواعيد02 — توسعات القراءة والحجز العام المطلوبة قبل التطبيق

التاريخ:2026-11-12. الحالة: **معتمد بقول المستخدم «أعتمد مقترح02 كما هو»؛ بدأ التنفيذ بعد تسجيل الإذن**.
المصدر [تذكرة02](issues/02-daily-appointments-and-patient-file.md) و[المواصفة](spec.md). موافقة01 حُصرت صراحةً في واجهاتها ولا تشمل هذه التوسعات. تبقى01 حاجز الإنجاز قبل تطبيق02، وتُقرأ حالتها الفعلية في [الفهرس](map.md).

## القاعدة الحالية والحاجة

تقدم المرضى بعد01 مرجعًا مفردًا للحجز بلا هاتف، ولا بحثًا معلنًا أو إسقاطًا جماعيًا لعرض المواعيد. تقدم الموظفون اختيار أطباء نشطين ومرجع طبيب مفردًا، دون إسقاط جماعي لمنشئي الحجوزات وأطبائها السابقين. قراءة ملفات المرضى أو قائمة الموظفين الحالية تتطلب صلاحيات مستقلة؛ استعمالها للحجز العام سيمنع صاحب إدارة المواعيد وحدها أو يكشف تفاصيل زائدة، ولن يحقق العزل المطلوب. المواعيد لا يجوز أن تقرأ جداول المرضى أو الموظفين أو الأدوار مباشرةً.

في الواجهة لا يوجد الآن مسار مواعيد في `client/app/navigation.ts`. renderAppointments المعتمد في01 يسمح بتركيب قسم الملف عبرapp، لكنه لا ينشئ شاشة اليوم تلقائيًا.

## التغيير المحدد المطلوب

### 1. عمليات المرضى المعلنة

إضافة نوع `AppointmentPatientSummary = { id: string; name: string; phone: string; fileNumber: string; archived: boolean }` وعمليتين إلى PatientsOperations، مع تصدير النوع المختار عبرindex:

```ts
searchAppointmentPatients(clinicId: string, input: { q: string; page: number }):
  Promise<{ items: AppointmentPatientSummary[]; page: number; hasNext: boolean }>;
appointmentReferences(clinicId: string, patientIds: readonly string[], q?: string):
  Promise<AppointmentPatientSummary[]>;
```

البحث الأول يختار النشطين فقط، بالاسم أو الهاتف أو رقم الملف وفق تطبيع المرضى القائم، بصفحات25. تستعمله نافذة الحجز بعد تحقق `appointments.write`، ولو لم يملك المنفذ `patients.read`. الثانية تقرأ فقط المعرفات المطلوبة من العيادة نفسها، وتشمل المؤرشف لعرض الحجز القائم؛ q اختياري يقيد هذه المجموعة بالبحث نفسه عند تصفية الجدول. لا تعيد عنوانًا أو ملاحظة إدارية للملف أو بيانات طبية أو جنسًا أو ميلادًا أو مفاتيح تخزين. تقسم الخدمة المعرفات إلى دفعات تقنية عند الحاجة دون إسقاط سجلات أو سقف أعمال للعدد.

تبقى appointmentReference المفردة المعتمدة في01 وقواعد الحجز والأرشفة كما هي. هذه عمليات داخلية بلا HTTP عام في المرضى؛ تملك المرضى الوصول إلى بياناتها وتطبيع البحث، وتملك المواعيد التفويض المحدد للاستدعاء.

### 2. عمليات الموظفين المعلنة

إضافة نوع `AppointmentStaffReference = { id: string; name: string; eligible: boolean }` وعملية واحدة إلى EmployeesOperations:

```ts
appointmentStaffReferences(clinicId: string, userIds: readonly string[]):
  Promise<AppointmentStaffReference[]>;
```

تقتصر على معرفات العيادة المطلوبة وتعيد الاسم والأهلية الحالية فقط؛ تشمل غير النشط والمنزوع منه دور الطبيب لأن الطبيب والمنشئ في التاريخ لا يُمحوان بتغير الأهلية. أهلية الطبيب من النشاط ودورdentist عبر RolesOperations الموجودة؛ لا توسعة للأدوار، ولا حسابات أو تجزئات أو أسماء دخول في المخرجات. يستخدم المواعيد النتيجة لإظهار أسماء الأطباء والمنفذين والتنبيه، ولا يفسر عدم أهلية المنشئ بوصفه خطأ إنشاء سابق.

### 3. المعاملات والتفويض وملكية القراءة

تستعمل المواعيد AppointmentsScope وأداة المعاملات المعتمدتين في01، فتقرأ البيانات المرجعية والموعد وتعيد فحص صلاحية المنفذ داخل المعاملة نفسها بعد قفل العيادة القائم. لا تغيير لـTransactionManager العام أو ملكية المستودعات، ولا وصول لجداول غير المواعيد في مستودعها. لا مخطط أو ترحيل جديد متوقع لتذكرة02؛ يحتفظ التخزين بالهويات الأصلية، وتُعرض الأسماء الحالية عبر مالكيها دون إنشاء نسخ أسماء تاريخية جديدة.

إنشاء موعد واختيار مريض أو طبيب للحجز: إدارة المواعيد. قراءة القائمة والتفاصيل وسجل الإنشاء: عرض المواعيد. قسم الملف: عرض المواعيد وقراءة المرضى معًا، ويُعاد التحقق من الشرطين في عملية قراءة القسم، ولا تكفي حراسة الزر. يُمنع مدير البرنامج والعيادة الأخرى. صاحب الإدارة وحدها يرى تأكيد الإنشاء واختيارًا محدودًا ولا يرى قائمة فارغة توهم قراءة جدول أو تفاصيل حجز قائم. لا تغيير لمنح الأدوار أو الحسابات.

## العقود الخارجية المقترحة

- `GET /api/clinic/appointments/patients?q=&page=1`: إدارة المواعيد؛ بحث المرضى النشطين المحدود أعلاه. مسار ثابت قبل/:id، ولا يتيح فتح ملف المريض.
- `GET /api/clinic/appointments?date=YYYY-MM-DD&doctorId=&status=&q=&page=1`: عرض المواعيد؛ يوم بتوقيتAfrica/Nouakchott، كل الحالات افتراضيًا، ترتيب بالبداية ثمid، صفحات50 معhasNext وعدد إجمالي للفترة بعد التصفية. يمكن الوصول إلى كل النتائج بصفحات صريحة؛ لا حد أعمال للعدد. الصلاحيات والردود القديمة لا تعيد بيانات محجوبة.
- `GET /api/clinic/appointments/patient/:patientId?page=1`: عرض المواعيد وقراءة المرضى؛ قسم مواعيد المريض نفسه، أحدث بداية أولًا، كل الحالات، صفحات50. هذا القسم لا يحتاج تاريخ يوم كي لا يخفي حجوزات المريض القادمة أو السابقة. لا زيارات أو مالية.
- `GET /api/clinic/appointments/:id`: عرض المواعيد؛ التفاصيل المحدودة وسجل الإنشاء المنفذ في01. يتضمن هاتف المريض والملاحظة الإدارية للحجز، وأسماء المنفذين ووقت الإنشاء والقيم المسجلة. لا منفذ تعديل أو حالات في02؛ تأتي04 لاحقًا.
- توسيع سماح `GET /api/clinic/appointments/doctors` إلى العرض أو الإدارة لمرجع اختيار الأطباء المحدود؛ يظل نشطين مؤهلين فقط. في فلاتر اليوم تُضم أسماء أطباء الحجوزات الظاهرة حتى إن صاروا غير مؤهلين؛ لا يحوّل هذا إدخالهم إلى خيار صالح لحجز جديد.

صف القائمة: `{ id, patient:{id,name,fileNumber,archived}, doctor:{id,name,eligible}, startsAt, endsAt, status, editVersion }`، والهاتف والملاحظة في التفاصيل فقط. لا تُرفق قوائم مرضى كاملة أو بيانات موظفين بالتفاصيل. ردود401/403 تعكس الجلسة والصلاحية،404 للمفقود أو خارج العيادة دون كشف،400 للمدخلات،500 عام. عمليات الكتابة وعقدها في01 يبقيان كما هما.

لا بحث مباشر من مستودع المواعيد في جداول المرضى: يستخرج معرفات حجوزات اليوم الموافق للفلاتر الأساسية، ويستعمل إسقاط المرضى معq، ثم يطبق مجموعة المعرفات الناتجة على استعلام المواعيد قبل التقسيم إلى صفحات، حتى لا تكون التصفية مقتصرة على الصفحة المحملة. تفاصيل عناصر المستودع الداخلية لا تُصدر خارج المواعيد.

## تركيب الواجهة المطلوب

إضافة مسارapp `/clinic/appointments` إلى تعريفات التوجيه والحراسة والقائمة الجانبية تحت صلاحية العرض أو الإدارة. تبقىapp مالكة المسار وcallbacks وحراسة المسودات، ولا أعمال عبرloaders/actions. تعلن المواعيد `AppointmentsPage` لشاشة اليوم والحجز العام، و`PatientAppointments` لقسم الملف. يركبapp القسم عبرrenderAppointments المعتمد في01؛ لا استيراد بين ميزتي المرضى والمواعيد.

تظل BookingAction للحجز من الملف؛ تستخدم نافذة الحجز نفسها في الصفحة العامة مع اختيار المريض المحدود عند غياب مريض ثابت. جميع طلبات المواعيد وQuery keys والمسوّدات والترجمات مملوكة حسب النمط القائم: طلباتالميزة، ترجمةshared/i18n، Radixعبرclient/ui، cacheجلسة في الذاكرة وpollingللبياناتالمعروضة فقط وحراسةالإغلاقوالتنقل. لا اعتماد مكتبة أو مخزن عام أو استثناء فحص. التسجيل داخل الحجز ليس جزءًا من02 ولا يظهر زر غير منفذ؛ تذكرة03 تتولاه.

## الملفات والمخاطر والبديل

الملفات المتأثرة بعد الإذن: dto/service/repository/index فيpatients وemployees، وقراءاتappointments وعقودها ومساراتها واختباراتها، وميزةappointments فيclient، وapp/navigation وApp وAppSidebar وحراسةالصلاحيات، وملفاتالترجمةوالتوثيق. لا تغيير لقواعد المعمارية أو منح أو بيانات المستخدم. قبل التطبيق تُسجل الموافقة وتحدث المراجع المعمارية وعقدالشاشات.

المخاطر: إسقاط جماعي أو بحث دون تقييد بالعيادة قد يكشف بيانات؛ يثبت العزل والتفويض فيHTTP وباختباراتمصطنعة. جمع معرفات فترة مزدحمة يزيد كلفة القراءة؛ يُحصر بالفترة والعيادة وتُختبر الصفحات والبحث قبل التقسيم، دون حذف نتائج أو سقف أعمال خفي. استعمال قفل العيادة للقراءة يضيف انتظارًا لكنه يبقي التصميم الحالي؛ لا يُستبدل بنمط معاملات مختلف دون قرار جديد.

البديل بواجهات المرضى والموظفين العامة الحالية يحتاج صلاحيات زائدة ويكشف حقولًا غير لازمة؛ والاستعلام المباشر عن جداولهم محظور. المقترح يضيف ثلاث عمليات محدودة مع الحفاظ على الملكية والمعاملة المعتمدتين.

**الموافقة المسجلة تخص هذا النطاق02 فقط**: العمليات الثلاث وأنواع إسقاطها، وتوسيع إذن مرجع الأطباء، وعقود القراءة، ومسارapp وتركيب قسم الملف والنافذة المشتركة. لا تشمل03–05 أو تسهيل فحوص أوPR/push/نشر. سُجل الإذن في مراجع المعمارية وعقد الشاشات قبل الكود؛ لا يعني هذا اكتمال التنفيذ.
