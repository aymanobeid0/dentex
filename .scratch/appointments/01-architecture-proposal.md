## الواقع الذي فُحص في المصدر

- `PatientsOperations` في `server/modules/patients/patients.dto.ts` لا تقدم إلا `initializeNumbering`. لا توجد عملية معلنة لمرجع مريض وأهليته للحجز.
- `EmployeesOperations` في `server/modules/employees/employees.dto.ts` تقدم عمليات الحسابات والمصادقة والإدارة، ولا تقدم اختيار طبيب للحجز. `RolesOperations.assigned` موجودة بالفعل؛ لا حاجة لتوسيع واجهة الأدوار في01.
- `server/infrastructure/application.ts` يعيد بناء صلاحيات المنفذ بعد `clinics.lockForMutation`، ويربط عمليات الموديولات بالمعاملة نفسها. تعديل الموظف وأدواره ومنح الأدوار وأرشفة المريض تستخدم قفل العيادة نفسه بالفعل.
- واجهة المرضى في المتصفح تعلن `PatientPage` و`PatientView` فقط. تركيبها الحالي لا يتيح للتطبيق وضع إجراء مواعيد في الملف دون تعديل معلن.
- لا جداول مواعيد في المخطط. صلاحيتا `appointments.read` و`appointments.write` موجودتان؛ لا نضيف صلاحيات أو نغير منح الحسابات.

## التغيير المطلوب اعتماده للشريحة01 فقط

### 1. واجهات الخادم المعلنة

إضافة العقود التالية، مع تصدير أنواعها المختارة عبر `index.ts` لكل ميزة؛ لا مستودعات ولا Prisma في الواجهة:

```ts
// patients
type AppointmentPatientReference = {
  id: string; name: string; fileNumber: string; archived: boolean;
};
// ضمن PatientsOperations
appointmentReference(clinicId: string, patientId: string):
  Promise<AppointmentPatientReference | null>;

// employees
type AppointmentDoctorReference = { id: string; name: string; eligible: boolean };
// ضمن EmployeesOperations
appointmentDoctors(clinicId: string):
  Promise<Array<{ id: string; name: string }>>;
appointmentDoctor(clinicId: string, doctorId: string):
  Promise<AppointmentDoctorReference | null>;
```

`appointmentReference` تقرأ داخل المرضى فقط، وتعيد null للمفقود أو خارج العيادة. `appointmentDoctors` تعيد النشطين حاملي دور `dentist` في العيادة، بما فيهم المدير الذي يحمل الدور؛ لا اسم دخول أو هاتف أو بيانات اعتماد. `appointmentDoctor` تحسب الأهلية من النشاط والدور الحاليين عبر واجهة الأدوار الموجودة؛ لا استيراد مستودع الأدوار. تنفذ المستودعات إسقاطات الحقول المطلوبة دون تحميل ملف طبي أو تجزئة كلمة مرور لهذه العمليات. هذه عمليات داخلية معلنة، وليست منافذ HTTP غير محمية.

تظل المواعيد مسؤولة عن تفويض استدعائها حسب العملية. المساران في01 خاصان بجلسة موظف عيادة مخوّل بالإنشاء، مع فحص جديد داخل المعاملة؛ لا تمنح هذه العمليات قراءة عامة للمرضى أو الموظفين. قراءة الملف الحالية تبقى محمية بصلاحيتها المستقلة.

### 2. الربط بالمعاملة وضمان التداخل

إضافة `AppointmentsScope` يحتوي مستودع المواعيد نفسه وواجهتي المرضى والموظفين المعلنتين وحقائق صلاحية المنفذ. يربط composition root هذه العناصر جميعًا بمعاملة Prisma واحدة بعد قفل صف العيادة القائم. لا تغيير لواجهة `TransactionManager` العامة، ولا كشف مستودعات موديول آخر، ولا أقفال استشارية أو معاملات متداخلة.

ترتيب الإنشاء: قفل العيادة ← إعادة فحص جلسة المنفذ و`appointments.write` أو دور المدير ← مرجع المريض وعدم أرشفته ← أهلية الطبيب ← تحقق الوقت والتداخل ← إدراج الموعد وسجل إنشائه ← commit. كل خطأ يتراجع عن الموعد وسجله معًا. يشترك هذا القفل مع عمليات تغيير الأهلية القائمة، فلا تبقى صلاحية أو أهلية قديمة بين التحقق والحفظ. كلفته تسلسل الكتابات الحساسة داخل العيادة؛ لا يتوسع إلى قفل كل العيادات.

أقترح حماية إضافية داخل PostgreSQL بقيدي `EXCLUDE USING gist` على جدول المواعيد: `(clinic_id WITH =, doctor_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)`، ومثله لـ`patient_id`، وكلاهما بشرط `status IN ('booked', 'attended')`. تتطلب المساواة على UUID امتداد `btree_gist`. المجال نصف المفتوح يسمح بالتتابع. يفحص المستودع التعارض لإرجاع خطأ مفهوم، ويحول إخفاق أي من القيدين إلى `appointment_overlap` دون كشف الموعد الآخر. يتحقق الاختبار أيضًا من القيد مباشرةً بكتابات متزامنة على القاعدة المصطنعة، وليس طلبات التطبيق وحدها.

هذا استعمال موثق لـ[قيود مجالات PostgreSQL](https://www.postgresql.org/docs/current/rangetypes.html#RANGETYPES-CONSTRAINT) و[btree_gist](https://www.postgresql.org/docs/current/btree-gist.html). إذا لم يتوفر الامتداد أو إذن إنشائه في بيئة مستهدفة، يتوقف ترحيلها مع بيان السبب؛ لا حذف للقيد أو تغيير منح تلقائي لتجاوزه.

### 3. التخزين الجديد المملوك للمواعيد

ترحيل إضافي فقط لإنشاء `appointments` و`appointment_changes` والامتداد والقيدين. حقول الموعد: UUID، العيادة، المريض، الطبيب، البداية والنهاية بـtimestamptz، الحالة، ملاحظة إدارية اختيارية، `edit_version` يبدأ1، المنشئ، ووقت الإنشاء والتحديث. يفرض التخزين حالة صحيحة وبداية بدقيقة كاملة ومدة5–240 دقيقة بمضاعفات5 وعدم عبور يوم العيادة، مع السماح بمنتصف الليل كنهاية. الحاضر/المستقبل قاعدة خدمة وقت الإنشاء وإعادة الجدولة، وليست CHECK تتغير صلاحيتها بمرور الزمن.

علاقات مركبة مع العيادة والمريض والطبيب والمنشئ تمنع الربط العابر للعيادات. العلاقات لا تسمح بحذف السجلات المرجعية تلقائيًا. مجرد تعريف FK في المخطط لا يجيز للمستودع قراءة جداول الموديولات الأخرى. سجل الإنشاء يحمل المنفذ والوقت والقيم المنشأة، وbefore=null؛ لا نسخ دائمة من أسماء المرضى أو الموظفين. زيادة الإصدار وbefore/after للتعديلات لاحقًا في04 ضمن المعاملة نفسها؛ لا منفذ تعديل أو حالات مبكر في01.

تُجرّب الترحيلات والقيود على قاعدة مصطنعة مثبتة العزل أولًا. لا reset أو seed أو تغيير حسابات أو منح أو بيانات ملفات قائمة؛ لا تشغيل اختبارات على `dentex_dev`. يُثبت مسار نسخة التطوير وقاعدتها قبل تسليمها للفحص، وتُوثق نتيجة أي ترحيل فعلي دون أسرار، ولا يُدّعى تطبيقه من هذا المقترح.

### 4. تركيب الواجهة عبر app

تعلن المرضى نوعًا محدودًا `PatientAppointmentContext = { id; name; fileNumber; archived }`، وتضيف إلى `PatientPage` خاصية اختيارية `renderAppointments?: (patient: PatientAppointmentContext) => ReactNode`. تستدعيها في عرض ملف مقروء محمّل، خارج نموذج التحرير. يمرر app دالة تركّب إجراء الحجز المعلن من ميزة المواعيد؛ لا تستورد المرضى المواعيد أو العكس، ولا يكتب app طلبات أعمال. مفتاح المريض والجلسة يعزل النافذة والمسودة.

في01 تعرض هذه الفتحة زر الحجز ونافذته فقط، ويظهر الإجراء للمخول بالإدارة؛ المريض المؤرشف لا يقبل حجزًا. تملك المواعيد المدخلات والمسودة وHTTP وQuery وحراسة الإغلاق والتنقل، وتتلقى اللغة والصلاحيات وcallback انتهاء الجلسة ونقطة ربط حراسة التنقل بالنمط القائم. Radix عبر `client/ui` والتصميم الحالي مستمران. لا مسار متصفح جديد لهذه النافذة ولا اعتماد مكتبة جديد.

## عقد HTTP المقترح قبل الكود

- `GET /api/clinic/appointments/doctors`: يتطلب إدارة المواعيد، ويعيد `{ items: [{ id, name }] }` فقط بعد التحقق الحالي. لا يتطلب إدارة الموظفين ولا يعرض جدول المواعيد.
- `POST /api/clinic/appointments`: يتطلب إدارة المواعيد والمصدر الموثوق؛ يقبل `{ patientId, doctorId, date: 'YYYY-MM-DD', time: 'HH:mm', durationMinutes, administrativeNote? }`. التاريخ والوقت مدنيان بتوقيت `Africa/Nouakchott`، ولا يرسل العميل عيادة أو حالة أو منشئًا أو نهاية. تُشتق النهاية على الخادم، والملاحظة بعد trim حتى2000 حرف كحد تقني معلن مماثل للملاحظات الإدارية القائمة.
- نجاح201 محدود: `{ id, patientId, doctorId, startsAt, endsAt, status: 'booked', editVersion: 1 }`، والأوقات ISO بمرجع UTC. لا أسماء أو هاتف أو جدول أو تاريخ تغييرات في تأكيد الإنشاء. يستعمل العرض هوية المريض والطبيب المسموح اختيارهما، ولا يعتبرها المرجع للحفظ.
- أخطاء:400 `invalid_input` للحقول/الوقت غير الصالح،401 للجلسة،403 للمنع/المصدر،404 `appointment_reference_not_found` للمريض أو الطبيب غير الموجود أو خارج العيادة دون تمييز،409 `patient_archived` أو`doctor_ineligible` أو`appointment_in_past` أو`appointment_overlap`. أخطاء500 تبقى عامة. لا معرّف أو اسم أو وقت لحجز متعارض داخل الخطأ.
- لا retry للكتابة؛ تمنع الواجهة الإرسال المكرر أثناء الطلب. فقد الرد أو رد نجاح تالف نتيجة غير مؤكدة تحفظ المسودة وتحجب إعادة الحفظ وتطلب مراجعة مخوّل بالعرض. لا قراءة مواعيد خاصة مؤقتة لتجاوز غياب شاشة02، ولا افتراض idempotency. إثبات التخزين في QA01 من القاعدة المصطنعة؛ واجهة القراءة العامة تبدأ في02.

## الملفات والأثر والبدائل

الملفات المتأثرة بعد الإذن: dto/service/repository/index للمرضى والموظفين؛ ملفات appointments بالقالب المعتمد؛ `server/infrastructure/application.ts` ومواضع تركيب المسارات ومعالج الأخطاء؛ `prisma/schema.prisma` وترحيل جديد؛ ميزة `client/features/appointments` وواجهة `PatientPage` وصادرات المرضى وتركيب app، والاختبارات والعقد والتوثيق. لا تعديل لقواعد المعمارية أو تخفيفها. تُحدّث وثيقتا المعمارية وعقد الشاشات بالنطاق الموافق عليه **بعد** وصول الإذن وقبل كوده.

البديل دون هذه التوسعات هو استخدام واجهات HTTP الحالية أو مستودعات الآخرين: الأولى تتطلب صلاحيات زائدة وتفصل فحص الأهلية عن المعاملة، والثانية محظورة. لا يوجد حاليًا عقد معلن ينجز01 كاملة دون توسعة. يمكن الاكتفاء بقفل العيادة وفحص التداخل، لكنه يعتمد على التزام كل مسار كتابة بالقفل؛ قيدا التخزين يضيفان ضمانًا مستقلًا مقابل اعتماد `btree_gist` وكلفة فهرسين. المقترح يختار القفل القائم مع القيدين ولا يغير حدود الملكية.

الموافقة المطلوبة تخص البنود1–4 وضمان التخزين وعقد01 المحدد هنا فقط. لا تشمل واجهات البحث المحدود للمرضى أو التسجيل داخل الحجز أو القراءة والتعديل والتقويم في02–05؛ تُعد تفاصيلها عند حواجزها ويُعرض ما يستلزم قرارًا جديدًا قبل تطبيقه. لا PR أو push أو نشر ضمن هذا الإذن.
