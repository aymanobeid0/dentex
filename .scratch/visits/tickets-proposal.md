# تقسيم إدارة الحضور والانتظار والزيارات — معتمد

التاريخ: 2026-11-13. اعتمد المستخدم طريقة الاختبار والتقسيم الخماسي واعتمادياته بقوله «نعم، أعتمد طريقة الاختبار والتقسيم الخماسي واعتمادياته؛ انشر المواصفة والتذاكر محليًا». نُشرت [المواصفة](spec.md) و[خمس تذاكر مستقلة وفهرسها](map.md)؛ جميعها ready-for-agent وnot-started. لا بدء تنفيذ ضمن الإذن.

## طريقة الاختبار المعتمدة

واجهة HTTP العامة مع قاعدة اختبار حقيقية معزولة هي نقطة الاختبار الأساسية القائمة، دون mocks لكل طبقة. تكملها اختبارات سلوك الواجهة والتحقق الفعلي من المسار إلى التخزين بالعربية والفرنسية والهاتف والمكتب ولوحة المفاتيح. تشمل التزامن والتراجع وفقد الرد والصلاحيات والعزل والإغلاق بتوقيت مضبوط. لا تُستخدم قاعدة التطوير أو حسابات المستخدم للاختبارات.

## التذاكر المعتمدة

### 01: تسجيل الحضور وإدارة انتظار الأطباء

**Blocked by:** None (can start immediately).

**What to build:** يسجل الموظف المخول حضور مريض مسجل، يختار طبيبه، ويرى الانتظار لكل طبيب مرتبًا بالوصول. ينقل المنتظر مع حفظ أولوية وصوله ويسجل مغادرته قبل الدخول. تسمح القائمة باختيار مريض غير الأول عند الحاجة دون تغيير وقت الوصول.

معايير القبول:

- المسار كامل من واجهة الاستخدام إلى HTTP والتخزين والعودة للقائمة؛ لا طبقة خادم منفصلة تنتظر تذكرة واجهة.
- تسجيل الوصول مستقل ولا ينشئ زيارة، مع دعم دون موعد، وحضور جارٍ واحد للمريض عبر جميع أطباء العيادة بما في ذلك الطلبات المتزامنة.
- اختيار الطبيب عند الوصول وقائمة مستقلة له، ونقل المنتظر مع حفظ وقت وصوله وأولويته.
- المغادرة قبل الدخول تنهي الانتظار دون زيارة؛ يمكن تسجيل حضور جديد بعد انتهائه.
- الأدوار الثلاثة تعرض المتابعة الإدارية لجميع أطباء العيادة وتنفذ نطاق هذه الشريحة، مع العزل واللغتين وحماية المسودة والحفظ.
- قبل الكود تُحدد عقود الاختيار والأهلية والصلاحيات والمقترح المعماري اللازم؛ لا يُفترض اعتماد تفاصيل لم تُحسم ولا تُغير منح الحسابات الفعلية تلقائيًا.

### 02: دخول الطبيب وسجل الزيارة وإنهاؤها

**Blocked by:** 01: تسجيل الحضور وإدارة انتظار الأطباء.

**What to build:** يدخل الموظف المريض من الانتظار إلى الطبيب، فينشأ سجل زيارة فعلية، ثم ينهيها وتظهر نتيجتها في متابعة الحضور. عند نسيان إنهاء السابقة يمكن تأكيد إنهائها وإدخال التالي.

معايير القبول:

- لا سجل زيارة قبل الدخول؛ الدخول يُعد زيارة سواء حدث إجراء علاجي أم لا، ودون طلب بيانات طبية.
- زيارة جارية واحدة للطبيب والمريض تحت التزامن؛ اكتمالها لا يعني انتهاء العلاج.
- يمكن إدخال منتظر غير الأول دون تحريف وقت الوصول.
- تنبيه باسم المريض السابق وإجراء مركب مؤكد لإنهائه وإدخال التالي؛ لا نجاح جزئي إذا تعذر الإدخال، ولا وقت مغادرة فعلي مختلق.
- عرض النتيجة والزيارة المسجلة ضمن متابعة المريض؛ لا حقول تشخيص أو مالية أو واجهات مستقبلية وهمية. شكل عرض التاريخ داخل ملف المريض ليس معتمدًا ضمنيًا، ويحدد عقد تركيبه قبل الكود.
- تُثبت الوظائف والصلاحيات واللغتان والعزل والتراجع وفقد الرد عبر المسار الكامل.

### 03: ربط الزيارة بالموعد وحفظ استقلال السجلين

**Blocked by:** 02: دخول الطبيب وسجل الزيارة وإنهاؤها.

**What to build:** يربط المخول زيارة بموعد المريض في اليوم نفسه اختياريًا، دون مزامنة الحالات، وتطبق قيود إعادة الجدولة التي تحافظ على الحضور والزيارة السابقين.

معايير القبول:

- يمكن وجود زيارة دون موعد أو دون رابط، ولا يؤدي تغيير الموعد إلى حضر إلى تسجيل حضور أو زيارة.
- الرابط للمريض واليوم نفسيهما، وكل موعد له زيارة واحدة كحد أقصى تحت التزامن.
- نقل الموعد قبل الدخول لا ينقل حضور اليوم إلى يوم آخر؛ الحضور الجديد يسجل عند العودة.
- بعد بدء الزيارة المرتبطة يمنع نقل الموعد إلى يوم آخر؛ المتابعة بموعد جديد دون تغيير السابقة.
- تبقى سائر قواعد المواعيد الحالية نافذة؛ لا فتح إعادة جدولة لحالة كانت تمنعها أصلًا أو تغيير المريض أو تخفيف منع التداخل.
- تحدد شروط مرجع الموعد غير المحسومة وتصحيح الرابط ضمن عقد الشريحة قبل تنفيذ الجزء المتأثر؛ أي توسعة واجهة بين المواعيد والحضور/الزيارات تعرض محددة للموافقة المعمارية قبل الكود.
- تحقق UI إلى API والتخزين للتغييرات والرفض والتزامن والعزل واستقلال الحالات باللغتين.

### 04: تصحيح الحالات وحذف تسجيل الحضور الخاطئ

**Blocked by:** 02: دخول الطبيب وسجل الزيارة وإنهاؤها.

**What to build:** يصحح الاستقبال والطبيب والمدير الحالة المسجلة بالخطأ مع تاريخ واضح للتغيير، ويحذفون نهائيًا حضورًا مسجلًا لمريض لم يحضر أصلًا.

معايير القبول:

- الأدوار الثلاثة تصحح حالات السجل الإداري لجميع أطباء عيادتها؛ السبب اختياري، والسابق والجديد والمنفذ والوقت محفوظة ومعروضة للمخول.
- لا يخرق التصحيح قيد المريض الواحد أو سعة الطبيب، ولا يعيد سجل يوم سابق إلى انتظار يوم جديد.
- الحذف النهائي يخص التسجيل الخاطئ لمن لم يحضر، ومتاح للأدوار الثلاثة؛ لا استبدال له بحالة تسجيل ملغى أو توسيع إلى حذف زيارة حدثت فعلًا.
- يستلزم الحذف تأكيدًا واضحًا وفق مكونات التطبيق القائمة، مع حماية الطلب المتكرر وفقد الرد والعزل. التأكيد مقترح تفاعل ضمن المراجعة، وليس تغييرًا لحق الحذف الذي اعتمده المستخدم.
- قبل تنفيذ تصحيح دخول مسجل خطأً، يحسم أثره على سجل الزيارة صراحةً دون تحويل الزيارة الفعلية إلى حذف غير مأذون. لا توقف الأجزاء المستقلة لهذا التصميم المفتوح.
- تُختبر الكتابة وسجل التصحيح وقراءته والحذف من الواجهة إلى التخزين، بما في ذلك التعارض ورفض المسارات غير المعتمدة.

### 05: إغلاق نهاية اليوم وتوضيح النتيجة غير المؤكدة

**Blocked by:** 02: دخول الطبيب وسجل الزيارة وإنهاؤها.

**What to build:** عند نهاية اليوم يغلق النظام الحضور المنتظر والزيارة الجارية بحالة مستقلة «أُغلقت تلقائيًا»، وتظهر النتيجة للمستخدم دون افتراض ما حدث فعليًا.

معايير القبول:

- الإغلاق التلقائي لا يسجل اكتمالًا أو مغادرة مؤكدة، ولا ينشئ زيارة لمن لم يدخل الطبيب.
- تحرير قيود الحضور الجاري وسعة الطبيب بعد الإغلاق يتيح تسجيل اليوم الجديد بصورة مستقلة.
- تُعرض حالة الإغلاق في متابعة الحضور والزيارة المسجلة، ولا تتحول إلى انتظار اليوم الجديد.
- تُحدد حدود اليوم بتوقيت العيادة وطريقة تدارك الإغلاق عند توقف الخادم قبل الكود؛ لا اعتماد لوقت جهاز الموظف أو جدولة خارجية جديدة ضمنيًا.
- الاختبار بتوقيت مضبوط يغطي نهاية اليوم والتشغيل المتكرر والتزامن مع إجراء الموظف، دون انتظار زمني طويل أو وصول لقاعدة التطوير.
- لا تحتاج هذه الشريحة ربط المواعيد أو واجهة التصحيح؛ اعتمادياتها على دورة الحضور والزيارة فقط.

## لماذا خمس شرائح؟

كل شريحة تقدم سلوكًا قابلًا للعرض والتحقق من الواجهة إلى التخزين، وتضم اختبارات نطاقها وفحوصها. لا تذكرة مخطط أو خادم أو واجهة أو اختبار أفقي مستقل. لا توجد إعادة تنظيم واسعة ثبتت ضرورتها تستلزم تذكرة تمهيدية؛ لا تُنشأ إعادة تنظيم استباقية.

الاعتماديات الفعلية: 01 ← 02؛ ثم تعتمد03 و04 و05 على02، دون تسلسل مصطنع بينها. المقصود استقلال بوابات البدء، وليس إذن العمل المتوازي أو نشر تطبيق جزئي قبل اكتمال السلوك اليومي. مراجعة تكامل التصحيح مع الرابط والإغلاق بعد اجتماعها لازمة ضمن الشرائح، دون تأجيل اختبارات الأساس إلى تذكرة أخيرة.

## بوابات مشتركة قبل التنفيذ والإتمام

- بعد اعتماد المستخدم نُشرت المواصفة والتذاكر بتصنيف ready-for-agent، والتنفيذ not-started. حُفظت الاعتماديات المعتمدة دون إضافة تسلسل بين03 و04 و05.
- الاعتماديات المذكورة بين التذاكر فقط؛ بوابات الموافقة المعمارية والعقود وتفاصيل المجال المفتوحة قائمة في الشريحة المتأثرة ولا يخفيها تصنيف الجاهزية.
- أي تقييد أو توسعة لحق من حقوق المستخدم غير محسومين لا يصبح قاعدة معتمدة باعتماد التقسيم. إعداد العقد المراجع جزء من الشريحة قبل كود الجزء المتأثر، لا تذكرة برمجة أفقية جديدة.
- تلتزم كل شريحة بالمعمارية والمكونات المشتركة وRadix وإدارة الحالة واللغتين. عقود التكامل الجديدة تحتاج الإذن المحدد وفق إجراء المشروع، لا اعتمادًا عامًا لهذا التقسيم.
- الفحص والمراجعة يشملان أحدث main المجلوب عند التنفيذ والجديد وغير الملتزم به؛ تحفظ بيانات التطوير وحساباتها وتترك النسخة الصحيحة تعمل لفحص المستخدم قبل PR.
- لا تنفيذ أو تغيير بيانات أو تشغيل أو اختبار تطبيق أو رفع أو نشر حدث لإعداد المقترح.

## نتيجة الاعتماد والنشر

اعتمد المستخدم طريقة الاختبار وحجم الشرائح الخمس واعتمادياتها وأذن بنشرها محليًا؛ نُشرت دون دمج أو تقسيم إضافي ودون بدء كود. يحفظ الفهرس روابط الملفات وحالة التنفيذ، وتبقى تفاصيل المجال المفتوحة والموافقات المعمارية في الجزء المتأثر كما وُصفت دون موافقة ضمنية عليها.
