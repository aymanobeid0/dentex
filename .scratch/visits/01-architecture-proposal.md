التاريخ: 2026-11-13. الحالة: **مقترح ينتظر موافقة المستخدم؛ لا موافقة أو تنفيذ ضمني**.

النطاق: [التذكرة01](issues/01-attendance-and-doctor-queues.md) وقصصها فقط؛ المرجع [المواصفة](spec.md) و[خلاصة القرار](decision-summary.md). تكليف التنفيذ الحالي يشمل التذاكر الخمس، لكنه لا يحسم التفاصيل المفتوحة. baseline الذي جلبه الوكيل الأب حديثًا: `3dfb963e72871e7103ce3d863124e82ac7661ac6`، على `codex/attendance-visits-integration`. هذا إعداد تصميم، لا مراجعة إتمام ولا نتائج اختبارات.

## ما أثبته المصدر الحالي

- لا يوجد مخزن حضور أو زيارات أو صلاحيات لهما في `prisma/schema.prisma` أو `roles.schemas.ts`. الموجود مواعيد مستقلة وسجل تغييرها؛ لا يصح استعمال صف الموعد كحضور.
- `PatientsOperations` المعلنة في `server/modules/patients/index.ts` تتيح `appointmentReference(clinicId,id)` بالإسقاط `{id,name,fileNumber,archived}`، و`appointmentReferences(clinicId,ids,q?)` التي تضيف الهاتف وتشمل المؤرشف، و`searchAppointmentPatients(clinicId,{q,page})` التي تحصر النشطين بصفحات25. البحث الداخلي القائم يدعم الاسم والهاتف المطبع ورقم الملف. هذه العمليات وافق عليها المستخدم للمواعيد تحديدًا؛ لا يمتد الإذن للحضور تلقائيًا.
- `EmployeesOperations` تتيح `appointmentDoctors(clinicId)` للنشطين بدور `dentist`، و`appointmentDoctor(clinicId,id)` الذي يعيد `{id,name,eligible}`، و`appointmentStaffReferences(clinicId,ids)` الذي يتيح عرض اسم غير المؤهل أيضًا. حساب الأهلية داخل الموظفين باستخدام `RolesOperations.assigned`؛ ليس للمستهلك قراءة `users/user_roles/roles` مباشرة.
- `server/infrastructure/application.ts` ينشئ كل العمليات المرتبطة من Prisma transaction واحدة؛ `mutation()` يقفل العيادة عبر `clinics.lockForMutation` أولًا ثم يعيد تفويض المنفذ عبر `employees.authorization`. `AppointmentsScope` يعرض مستودعه فقط وواجهتي المرضى والموظفين. `TransactionManager<Scope,ClinicMutation>` عام بالفعل ولا يحتاج تعديلًا.
- الحماية الحالية تستخدم صلاحيات مخصصة في معظم الميزات وامتياز `admin`، مع مفاتيح دور `admin/dentist/receptionist`. لا توجد صلاحية حضور يمكن إعادة استخدامها دلاليًا؛ استخدام `appointments.write` سيجعل تغيير منح المواعيد يغير الحضور أيضًا دون قرار منتج.
- `client/app/navigation.ts` و`App.tsx` يملكان المسارات والحراسة؛ `AppSidebar` يملك عنصر التنقل. المواعيد تصدر صفحة ومكونات مختارة عبر `index.ts` وتملك HTTP/Query والمسودات. لا اعتماد بين ميزتين. `source/Queue.dc.html` مرجع شاشة عرض عام بأرقام أدوار وغرف وتقديرات انتظار وواتساب، وليس شاشة موظف معتمدة لهذا النطاق؛ لا ننقل هذه البيانات أو الوعود إلى المنتج.

## أ — المقترح المعماري المحدد المطلوب اعتماده

**الملكية:** Module واحدة باسم `visits` للحضور والانتظار والزيارة الإدارية معًا، لأن قيد حضور المريض الجاري وإنهاء حضوره وبدء زيارته قواعد مترابطة. تنفذ01 الحضور فقط؛02 تضيف الزيارة لاحقًا، ولا تنشئ01 زيارة شكلية. إنشاء Module وفق القالب route/controller/service/repository/schemas/dto/errors/index جزء من المعمارية المأذونة وليس استثناءً جديدًا. المطلوب موافقته هو تحديد هذه الملكية والواجهات العابرة وتركيبها الآتي، لا إعادة الموافقة على أصل الميزة.

المرضى يملكون هوية المريض وأرشفته؛ الموظفون يملكون الاسم وحالة النشاط وحساب أهلية الطبيب؛ الأدوار تملك إسناد الأدوار والمنح؛ المواعيد تملك حجوزاتها. `visits.repository` يقرأ ويكتب جداول الحضور التابعة له فقط، ولا يستعمل Prisma include للوصول لبيانات المريض أو الطبيب.

**أربع عمليات معلنة جديدة فقط**، بأسماء تخص المستهلك وتعيد أقل حقول لازمة:

```ts
// PatientsOperations؛ التصدير عبر patients/index.ts
type AttendancePatientReference = {
  id: string; name: string; fileNumber: string; archived: boolean;
};
attendanceReferences(clinicId: string, ids: readonly string[]):
  Promise<AttendancePatientReference[]>;
searchAttendancePatients(clinicId: string, input: {q: string; page: number}):
  Promise<{items: AttendancePatientReference[]; page: number; hasNext: boolean}>;

// EmployeesOperations؛ التصدير عبر employees/index.ts
type AttendanceDoctorReference = {id: string; name: string; eligible: boolean};
attendanceDoctors(clinicId: string): Promise<Array<{id: string; name: string}>>;
attendanceDoctorReferences(clinicId: string, ids: readonly string[]):
  Promise<AttendanceDoctorReference[]>;
```

تستخدم المراجع الجماعية للتحقق من معرف واحد ولإثراء القائمة دون عملية أخرى لكل صف؛ تعيد المراجع المؤرشف/غير المؤهل حتى يبقى السجل القائم قابلًا للعرض. بحث الاختيار يحصر النشطين وفق قرار الأهلية المقترح أدناه ولا يعيد الهاتف، مع دعمه كمدخل بحث وفق المطبع القائم. لا ترجع بيانات اتصال أو حقولًا طبية أو credentials أو منحًا. الغياب من عيادة الجلسة لا يميز عن معرف غير موجود. توحيد/إعادة استخدام استعلامات المستودع الخاصة داخل مالكها جائز دون تغيير الواجهات الحالية للمواعيد أو نتائجها.

**المعاملة:** `VisitsScope = {repository: VisitsRepository, patients: PatientsOperations, employees: EmployeesOperations, actor: ActorAccess|null}`. يربطه composition root في `server/infrastructure/application.ts` بـ`createTransactionManager<VisitsScope,ClinicMutation>` مستخدمًا `mutation(client,context)` القائم. كل قراءة حساسة أو كتابة تمر بهذا النطاق: قفل العيادة، تفويض حديث للمنفذ، مراجع الأهلية، تحقق الإصدار، ثم كتابة الحضور. لا repositories لميزة أخرى ولا Prisma في service ولا transaction داخل عمليات المراجع. تضبط معاملة القراءة أيضًا اتساق الأسماء والأهلية مع صفوف الانتظار، وفق سابقة المواعيد.

**البدائل المدروسة:** استعمال عمليات `appointment*` كما هي يقلل الصادرات لكنه يوسع إذنها المحدد سابقًا ويقرن الحضور بعقد اسمُه ونطاقُه للمواعيد؛ إعادة تسميتها جميعًا إلى مرجع عام توسع تغيير هذه الشريحة بلا داعٍ. إعادة استعمال HTTP المرضى/الموظفين تتطلب صلاحيات مستقلة وحقولًا أوسع وقراءات منفصلة عن المعاملة، فلا تصلح لقرار الكتابة الذري. الاستعلام المباشر عن جداولهم مخالف. نوصي بالعمليات الأربع المحدودة دون تغيير TransactionManager أو RolesOperations أو فحوص المعمارية.

## ب — توصيات المنتج المحددة المطلوبة لشريحة01

1. **التفويض دون تغيير أي منح:** نوصي أن يسمح نطاق الحضور01 مباشرة للموظف النشط ذي أحد الأدوار `admin` أو `dentist` أو `receptionist` في عيادة الجلسة؛ عرض جميع قوائم أطباء عيادته وتسجيل الوصول والنقل والمغادرة. لا مفاتيح صلاحيات جديدة في01، ولا اشتراط `patients.read` أو `appointments.*` لعرض الإسقاط المحدود، ولا تعديل `RolePermission` أو افتراضات منح العيادات الجديدة أو القائمة. يعاد التحقق داخل المعاملة، وتطابق الواجهة الشرط نفسه؛ مدير البرنامج ممنوع. **المقايضة الصريحة:** هذه العمليات مرتبطة بالدور، فلا يستطيع مدير العيادة تعطيل الحضور وحده عبر محرر المنح الحالي؛ سحب الدور يسحب الوصول. البديل إن أراد المستخدم تخصيصًا مستقلًا هو `attendance.read/write`، لكن ذلك يتطلب اعتماد سياسة منح جديدة وتمكين الأدوار القائمة بصورة منفصلة؛ لا ننفذه تلقائيًا. هذه توصية جديدة تنتظر الموافقة رغم أن الأدوار الثلاثة نفسها معتمدة إجمالًا.
2. **الأهلية:** تسجيل وصول جديد لمريض غير مؤرشف فقط، وإسناده/نقل انتظاره إلى موظف نشط يملك دور `dentist` وقت الكتابة. إذا أُرشف المريض أو فقد الطبيب النشاط/الدور بعد التسجيل، يبقى حضوره معروضًا باسمه وحالة عدم الأهلية؛ لا إغلاق أو نقل تلقائي. تسمح01 بالمغادرة رغم تغير الأهلية وبالنقل إلى طبيب مؤهل رغم عدم أهلية الطبيب القديم أو أرشفة المريض؛ التسجيل الجديد ما زال ممنوعًا للمؤرشف. أهلية بدء الزيارة وما بعد الدخول تحتاج عقد02 ولا تعتمد هنا.
3. **الوقت والترتيب:** يسجل الخادم لحظة الوصول الحالية، دون وقت يدوي أو تعديل بأثر رجعي في01. يوم العيادة بتوقيت `Africa/Nouakchott` القائم (UTC+00)، وترتيب الانتظار بـ`arrivedAt` ثم تسلسل وصول ثابت يولده التخزين لكسر التعادل؛ النقل لا يغيرهما. لا زر لتغيير ترتيب دائم: «تقديم مريض» يعني إمكانية اختيار أي منتظر للدخول في02؛ لا كتابة أولوية جديدة في01 ولا ادعاء اكتمال إجراء الدخول الآن. حتى05 تبقى كل حالات الانتظار الجارية ظاهرة ولو من يوم سابق مع تاريخها؛ لا إسقاطها عند منتصف الليل أو تحرير قيد المريض بتصفية اليوم فقط.
4. **الشاشة والإسقاط:** مسار app جديد `/clinic/visits` باسم «الحضور والانتظار»/ترجمة فرنسية مكافئة وعنصر شريط جانبي، وصفحة `VisitsPage` معلنة من `client/features/visits/index.ts`. قوائم مستقلة لكل طبيب تعرض الاسم، رقم الملف، وقت/تاريخ الوصول، حالة الأهلية، وإجراءي النقل والمغادرة، مع زر تسجيل الوصول. نافذة التسجيل تبحث عن المريض بعد مدخل غير فارغ وتختار طبيبًا عبر `SelectField` دون اختيار تلقائي. النقل في Modal والمغادرة بعد ConfirmDialog. لا هاتف أو تشخيص أو تسجيل مريض جديد أو ربط موعد أو قسم تاريخ بملف المريض في01. لا route/detail contract أو callback عابر لميزات أخرى لازم؛ app يركب الصفحة فقط ولا ينفذ طلباتها.

## عقد HTTP والتخزين المقترح الذي سيُثبت قبل أول دورة TDD

كل المسارات تحت `/api/clinic/visits` وتحت تفويض الفقرة ب1، محكومة بالجلسة وعيادتها. لا يقبل الجسم clinicId أو actorId أو arrivedAt.

| الطلب | النتيجة المقترحة |
| --- | --- |
| `GET /doctors` | `200 {items:[{id,name}]}` للمؤهلين للاختيار |
| `GET /patients?q=...&page=1` | بحث غير فارغ، صفحات25؛ `200 {items,page,hasNext}` بالإسقاط المحدود؛ الفارغ400 ولا قائمة ابتدائية |
| `GET /` | `200 {items:[AttendanceSnapshot], doctors:[AttendanceDoctorReference]}` لكل الانتظار الجاري في العيادة، مرتب بالوصول؛ يشمل الأطباء غير المؤهلين المرتبطين بانتظار حتى لا تختفي قوائمهم؛ لا حد عدد خفي أو تاريخ محذوف |
| `GET /:id` | `200 AttendanceSnapshot` للهوية المحلية سواء انتظارًا أو مغادرة، لمراجعة الحفظ غير المؤكد دون إعادة الطلب |
| `POST /` `{patientId,doctorId}` | `201 AttendanceSnapshot` بعد تأكيد العقد والتخزين |
| `PATCH /:id` `{kind:'transfer',doctorId,editVersion}` أو `{kind:'leave',editVersion}` | `200 AttendanceSnapshot`؛ النقل والمغادرة للمنتظر فقط |

`AttendanceSnapshot = {id, patient:{id,name,fileNumber,archived}, doctor:{id,name,eligible}, status:'waiting'|'left_before_entry', arrivedAt, recordedEndAt:null|string, editVersion}`. الحقول الزمنية ISO UTC. `recordedEndAt` وقت تسجيل المغادرة فقط، لا ادعاء زمن فعلي مجهول. قائمة الانتظار لا تحتاج سجل تصحيح أو تاريخ تعديلات01؛04 تضيف عقد التصحيح المأذون لاحقًا. لا تضاف حقول appointment أو جدول زيارة قبل شريحتيهما.

جدول `attendances` مملوك لـvisits: UUID، clinicId، patientId، doctorId، status، arrivedAt، arrivalSequence فريد يولده التخزين، recordedEndAt، createdBy، editVersion، createdAt/updatedAt؛ علاقات مرجعية مركبة `(clinicId,id)` لضمان تطابق العيادة دون منح ملكية جداول المراجع. قيد جزئي فريد `(clinicId,patientId)` حيث `status='waiting'` في01 يحمي التزامن؛ عندما تضيف02 حالة `with_doctor` توسع القيد ليشملها ضمن شريحتها. قيد اتساق نهاية الانتظار مع الحالة، وفهرس `(clinicId,doctorId,status,arrivedAt,arrivalSequence)`. لا حذف أو تحديث لصفوف قائمة. هذه إضافة تخزين بالشكل المعتاد وليست إذنًا بتطبيق migration علىdev الآن؛ التنفيذ يختبر الإضافة على قاعدة معزولة أولًا ثم يتبع إجراء حفظ/ترحيلdev المعتمد.

الأخطاء: `400 invalid_input`، `401 unauthorized` للجلسة الغائبة/المنتهية وفق البنية الحالية، `403 forbidden`، `404 not_found` للسجل/المرجع الغائب أو خارج النطاق دون كشف بيانات، `409 attendance_active` لتكرار الحضور، `patient_archived`، `doctor_ineligible`، `edit_conflict`، `attendance_not_waiting`. يعاد التحقق من الصلاحية قبل إعادة أي معلومات تعارض. mapping أخطاء التخزين داخل repository؛ أخطاء قواعد العمل داخل service؛ Zod في controller؛ المعالج المركزي القائم فقط.

تملك visits طلبات api وQuery وhooks والمسودات؛ cache في نطاق الجلسة وقراءة دورية معروضة فقط عبر `useDisplayedQuery`، ولا retry/offline queue للكتابة. لا يمحو polling المسودة. الرد المفقود يبقى غير مؤكد؛ تحديث يدوي عبر القراءة يعرض ما في الخادم ولا يطلق POST/PATCH جديدًا تلقائيًا ولا يستنتج نجاحًا. التزامن بإصدار الصف يحفظ مسودة النقل عند409. إعادة النقر ممنوعة أثناء الطلب. النجاح لا يعتمد على كود200/201 وحده بل صحة snapshot. الواجهة تستعمل Modal/ConfirmDialog/SelectField والبحث المشترك وuseDraftGuard القائم دون مكونات تحاكي Radix؛ كل مظهر عام عند مالكه فيui.

## أثر الملفات والتحقق والحدود

بعد الموافقة: ملفات visits الجديدة في server/client، dto/service/index للمرضى والموظفين مع إعادة استخدام خاصة داخل مستودعاتهم عند الحاجة، composition root وHTTP mount، Prisma migration additive، app/navigation/App/Sidebar وstyles import، ترجمات AR/FR ووثائق العقود/المعمارية. لا تعديل لقواعد الاعتماديات أو RolesOperations أو مفاتيح المنح أو بيانات الحسابات. معيار المظهر `docs/ui-components.md` وDESIGN؛ تخطيط شاشة الموظف جديد وفق البند ب4، وليس نقل لوحة Queue العامة. تتحقق المقاسات والألوان والتركيز واللمس في اللغتين والمكتب/التابلت/الهاتف.

طريقة الاختبار **معتمدة سلفًا** في spec؛ لا اختبارات جديدة هنا ولا ادعاء TDD. يبدأ التنفيذ بعد القرار بدورة رأسية: HTTP عام مع PostgreSQL معزولة يثبت تسجيلًا ثم قراءته؛ تليها التعارضات المتزامنة، نقل يحفظ الوصول، مغادرة ثم حضور جديد، عزل عيادتين ومدير البرنامج، فقد/تغير الدور، وتغير أهلية المراجع دون نتيجة جزئية. اختبارات الواجهة في seam المستخدم تثبت AR/FR والمسودة والإرسال مرة والرد المفقود والمراجعة الصريحة. لا mocks لطبقاتنا الداخلية. يستخدم الزمن المثبت للاختبار فقط دون endpoint منتج. لا داعي لاختبار rollback مصطنع لعمليتي كتابة عبر ميزتين في01 لأن المراجع قراءة فقط؛ يثبت رفض المرجع عدم إنشاء حضور، وتظل اختبارات TransactionManager القائمة لازمة.02 تختبر ذريّة العمليتين حين تضيفهما. يلزم check:architecture/frontend-architecture/ui-styles والأنواع والبناء والاختبارات ومراجعة main جديدة والمتصفح الحقيقي للمسار كاملًا. تظلdev وحساباتها/volume محفوظة، وتبقى نسخة صحيحة عاملة لفحص المستخدم قبلPR.

لا تنفيذ مستقلًا ذا قيمة يمكن إنجازه الآن: أول شريحة تسجيل/عرض تتطلب الملكية والواجهات والتفويض والأهلية والشاشة أعلاه. إنشاء ملفات أو اختبارات على عقد غير معتمد سيثبت افتراضًا مفتوحًا. المتاح المستقل هو إعداد هذا المقترح فقط؛ لم يُفحص محتوى الملفات المستثناة أو يغير.

**صيغة اعتماد واحدة محددة مقترحة:** «أعتمد مقترح01: ملكيةvisits والعمليات الأربع وربطها بالمعاملة القائمة، وسياسة الأدوار الثلاثة المباشرة دون مفاتيح أو تغيير منح، والأهلية والأوقات والترتيب والمسار والعقد المحددة فيه؛ يظل02–05 وما لم يشمله المقترح خاضعًا لبواباته». يجب تسجيل جواب المستخدم ونطاقه في المراجع المعمارية وعقد الشاشات قبل الكود؛ لا يسجل هذا الملف تلك الموافقة نيابة عنه.
