## نتيجة الحصر بعد التنفيذ

انتقلت كتابتا الدخول والخروج إلى mutations داخلauth. لم تبق نسخ API محلية موازية أو timers يدوية في الميزات. حُذفت saveEmployee غير المستخدمة فقط؛ submitEmployeeAction مستعملة داخليًا لإعادة التعيين فبقيت. جرى فحص استدعاءات API ومستهلكيها ومواضع fetch والتخزين فيclient؛ fetch المباشر محصور في النقل المشترك وبديل مزوده، وليس مخزن بيانات شاشة. يركّبApp مزود الجلسة والنقل لجميع الشاشات.

أصلح اختبار الشاشة فقد كلمة مرور الدخول عند الانقطاع: كانت شاشة الدخول تُزال وتُركب مجددًا لأن الجلسة المجهولة المؤكدة عوملت كفشل تحميل الهوية. أصبحتauth تعلنanonymous مشتقة منQuery، ويحفظapp شاشة الدخول القائمة عند الانقطاع. لا حالة حساب جديدة أو مصدر بيانات موازٍ. أبقيت حالة البداية التي لم تحمل هوية قط منفصلة وتعرض تعذر الاتصال بدل نموذج دخول مضلل.

يُرفض رد دخول200 غير مكتمل بوصفه غير مؤكد قبل استبدال الجلسة؛ فحصDTO محلي فيauth، وليس مشروع مخططات مشتركة.500/408 وفقد الرد غير مؤكدة، مع بقاء403 للمصدر و400/401 لبيانات الدخول. الخروج ينتظر204 فقط. تظل العمليات بلا إعادة تلقائية أو حفظ مؤجل، ولا تُخزن كلمات المرور في المفاتيح أو القرص. [التغطية44](09-coverage.md) و[التحقق النهائي](09-verification.md) يربطان النتائج والحدود.
