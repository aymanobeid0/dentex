# إدارة حالة الواجهة — نقاش قرار

Status: decided

سجل تاريخي للمقابلة. الأسئلة المفتوحة وصياغات انتظار الاعتماد أدناه حُسمت؛ المرجع الحالي [القرار المعتمد](../../docs/frontend-state.md) و[حالة التنفيذ](../frontend-state-migration/map.md).

2026-11-04: طلب المستخدم grill-with-docs لحسم إدارة الحالة وتوثيق القرار أثناء المقابلة. هذه ملاحظات نقاش وليست إذن تنفيذ أو ADR معتمدًا. الخادم وعقوده ومعماريته خارج نطاق التغيير.

## قرارات حسمها المستخدم

- TanStack Query لإدارة بيانات الخادم.
- عند العودة من ملف المريض إلى القائمة لا يُستعاد البحث السابق؛ يبدأ البحث فارغًا.

## الحقائق الحالية

الواجهة تعتمد useState/useEffect/useRef وfetch، مع حالة عامة في App تمرر عبر props. لا Context مخصص لحالة التطبيق أو Zustand أو Query حاليًا. Providers القائمة تخص Radix. المراجع client/main.tsx وclient/PatientPage.tsx وclient/usePatientSearch.ts. مواصفات الواجهة docs/ui-contract.md؛ قواعد الخادم docs/architecture.md وADR0001/0002 لا تتغير بهذا النقاش.

## شجرة القرار المفتوحة

1. حدود أدوات حالة العميل: محلية، Context محدد، ومخزن متخصص للحالة المشتركة المعقدة.
2. العمل أثناء انقطاع الاتصال: قراءة قديمة أم كتابة مؤجلة، وأثره على استمرارية المسودات.
3. حداثة بيانات الخادم وتغييرات مستخدم آخر: متى نعيد الجلب وما يستدعي اتصالًا لحظيًا لاحقًا.
4. فروع لاحقة حسب الإجابات: سياسة مسودات النماذج والتنقل، عزل cache ودورة الجلسة، سياسة retry/الإلغاء، حدود الميزة وواجهة hooks، ونطاق الانتقال والتحقق.

تُحسم القرارات في جولات وتُسجل الإجابات فور ورودها، ثم يعرض القرار النهائي للموافقة الصريحة قبل التنفيذ.

## الجولة الأولى — إجابات المستخدم المعتمدة

- حالة المكوّن محلية؛ Context للإعدادات مثل اللغة؛ Zustand عند ظهور حالة مشتركة معقدة، دون فرض تثبيته الآن.
- عند انقطاع الاتصال: إتاحة قراءة البيانات المحمّلة مع تنبيه؛ لا يُعتبر التعديل محفوظًا قبل تأكيد الخادم. لا صف كتابة offline معتمد.
- تغييرات مستخدم آخر تظهر تلقائيًا أثناء بقاء المستخدم في الشاشة، دون مغادرتها والعودة. لم تُحسم مهلة الوصول أو النقل أو نطاق الموارد بعد؛ لا يُفسر هذا كإذن بإضافة SSE/WebSocket أو تغيير الخادم قبل عرض القرار.

## الجولة التالية — نقاط تحتاج قرارًا

- حداثة تلقائية: المهلة المقبولة ونطاق البيانات، ثم اختيار النقل المناسب مع بيان أثره.
- تعارض التحديث الوارد مع مسودة يحررها المستخدم، وضمان عدم الكتابة فوق تعديل آخر عند الحفظ.
- مغادرة نموذج بمسودة غير محفوظة واستمراريتها؛ القراءة offline لا تحسم هذا وحدها.

حقائق إضافية: الرجوع إلى القائمة يعيد تركيب PatientList ويبدأ البحث فارغًا حاليًا. المسودات ذاكرة محلية فقط ولا تخزين لها بين إعادة التحميل؛ localStorage للغة وحدها. الهوية من /api/auth/me والجلسة cookie HttpOnly؛ العيادة يحددها الخادم، لا معرّف يثق به من طلب الواجهة.

## الجولة الثانية — إجابات المستخدم المعتمدة

- ظهور تعديلات الآخرين خلال نحو15 ثانية أثناء ظهور الشاشة، مع إعادة التحقق عند العودة؛ لا اشتراط تحديث شبه فوري حاليًا.
- مسودة المستخدم لا تستبدل ببيانات واردة. يُنبه بتعديل الآخر، ويُمنع الاستبدال المتعارض إلى حين المراجعة؛ وسيلة ضمان الخادم وحدود تطبيقها لم تحسم بعد.
- قبل مغادرة نموذج معدل غير محفوظ: البقاء أو المغادرة مع تجاهل المسودة. لا حفظ دائم للمسودات في المتصفح.

قراءة تقنية أولية: يناسب مهلة15 ثانية polling للموارد المعروضة فقط عبر TanStack Query عند ظهور التبويب، دون إضافة نقل SSE/WebSocket. هذا مقترح لا قرار نقل معتمد بعد. نطاق polling والانتقال وآثار منع التعارض على العقود قيد الحسم بعد التحقق من الكود.

## الجولة الثالثة — إجابات المستخدم المعتمدة

- إعادة جلب كل نحو15 ثانية للبيانات المعروضة فقط في الشاشات الحالية، مع التوقف بالخلفية أو دون اتصال وإعادة التحقق عند العودة.
- ترحيل بيانات API بجميع الشاشات الحالية عبر تذاكر متتابعة وفحص كل تذكرة، واعتماد النمط للميزات المستقبلية.

## نتيجة فحص عقود التعارض

المرضى حاليًا إنشاء وعرض دون endpoint تعديل. الموظفون يملكون PUT بيانات وأدوار وPATCH حالة، والأدوار PUT يستبدل المنح كاملة. لا expectedVersion أو ETag/If-Match لهذه الكتابات. credentialVersion يخص إبطال الجلسة ولا يكشف قدم نموذج الموظف أو الدور. أقفال المعاملات الحالية تحمي قواعد العزل والمدير الأخير، لكنها لا تمنع آخر حفظ من استبدال حقول أرسلها نموذج قديم.

المراجع: server/modules/{patients,employees,roles}/*.routes.ts وemployees.schemas.ts وroles.schemas.ts وprisma/schema.prisma وserver/infrastructure/application.ts. حماية التعارض الذرية تتطلب دعمًا صريحًا بعقد الخادم؛ version متزايد مع ترحيل مقترح قابل للفحص، لا يكفي polling أو فحص GET قبل الحفظ.

## قرار مفتوح قبل تجميع الصيغة النهائية

هل تُضم حماية تحرير الموظفين ومنح الأدوار إلى خطة مستقلة ضمن الانتقال، مع إصدار سجل وفحص ذري وعقد تعارض وترحيل عند الحاجة، أم تُؤجل كميزة لاحقة مع توثيق غياب الضمان؟ لا إضافة endpoint تعديل مرضى بسبب هذا القرار. لا تغيير لتنظيم route/controller/service/repository أو تخفيف فحوصه. لا تنفيذ قبل الموافقة النهائية.

## الجولة الرابعة — قرار حماية التعارض

وافق المستخدم صراحة على ضم حماية التعارض إلى الخطة بتذكرة مستقلة، مع تغيير العقود والترحيل اللازم ضمن المعمارية الحالية. نطاقها بيانات الموظفين وأدوارهم ومنح الأدوار؛ لا إضافة تحرير مرضى. أُعدت الصيغة الموحدة في docs/frontend-state.md بانتظار التأكيد النهائي. ضوابط cache في الذاكرة وعزل الجلسة والقراءات والكتابات ومعالجة نتيجة الحفظ المجهولة معروضة ضمن الصيغة، ولم تُعامل كإجابات سابقة.

شجرة القرارات الفردية حُسمت؛ الحدود والضوابط والتسلسل في الصيغة الموحدة للاعتماد أو التصحيح. لا تنفيذ حتى انتهاء المقابلة وطلب عمل واضح.
