# ترقيم ملفات المرضى لكل عيادة — مقابلة القرار

التاريخ:2026-11-04. الحالة: اكتملت المقابلة واعتمد المستخدم الفهم والخطة والتوسعة المحددة بقوله «تم الاعتماد». التنفيذ لم يبدأ؛ لا يُسجل اعتماد التصميم تغييرًا فعليًا للبيانات.

## المشكلة والمبدأ المحسوم

أوضح المستخدم أن عدّاد الملفات المشترك غير مقبول لأنه قد يكشف نشاط عيادات أخرى. المطلوب تسلسل تلقائي مستقل لكل عيادة، يبدأ من نقطة بداية ثم يزداد. حُدث تعريف رقم الملف فيGLOSSARY وفق هذا المعنى؛ لم يتغير الكود أو المخطط أو الترقيم القائم.

## الحقائق الحالية

- يولد PostgreSQL الأرقام عبرBIGSERIAL واحد لجدولpatients؛ تفرد(clinic_id,file_number) لا يفصل العدّاد.
- الروابط وGET تعرّف الملف بـUUID id؛ رقم الملف ظاهر ومستخدم في البحث. استقلال الرقم لا يستدعي تغيير روابط الملفات.
- المواصفة الحالية تحفظ رقم الملف ولا تعيد استخدامه بعد الأرشفة، ولا تشترط خلو التسلسل من الفجوات. معالجة الأرقام القائمة تتطلب قرارًا صريحًا، لا إعادة ترقيم ضمنية.
- لا فواتير منفذة؛ أي قاعدة لترقيمها هنا مبدأ مستقبلي، لا تنفيذ لميزة الفواتير.
- تبقى dentex_dev وvolume والحسابات وبيانات المستخدم محفوظة. أي انتقال بيانات أو تنظيم خارج المعمارية المعتمدة يحتاج موافقة المستخدم وفق docs/architecture.md.

## شجرة القرارات

1. محسوم: البداية الافتراضية١، مع إمكانية اختيار بداية مختلفة قبل أول مريض.
   - محسوم: مدير البرنامج يحددها عند إنشاء العيادة، وتبقى١ إن لم يغيرها. تُقفل بعد أول مريض؛ لا صلاحية تعديل أرقام فردية.
2. محسوم: السماح بالفجوات مع التفرد والتزايد داخل كل عيادة، وعدم إعادة استخدام الرقم بعد الأرشفة أو إعادة البدء السنوية.
3. محسوم بعد توضيح السؤال: لكل عيادة عدّاد فواتير مستقل عند تنفيذ الفواتير لاحقًا؛ تنفيذ المرحلة الحالية للمرضى فقط.
4. محسوم: اختار المستخدم إعادة ترقيم الملفات الموجودة لكل عيادة وفق بدايتها، مع خطة لحفظ المراجع القديمة. هذا تعديل مقصود لقاعدة ثبات الرقم للانتقال مرة واحدة؛ لا تغيير UUID أو حذف مرضى أو حسابات أو إعادة تهيئة.
   - محسوم: العيادات القائمة تبدأ من١، ويُعاد إسناد الأرقام بحسب الرقم القديم تصاعديًا داخل كل عيادة.
   - محسوم: سجل تحويل القديم إلى الجديد متاح لمدير العيادة فقط، والبحث المعتاد يستخدم الجديد فقط؛ لا بحث مختلط قد يفتح ملفًا خاطئًا.
5. معتمد: تصميم الكتابة والتزامن والانتقال والتحقق وتوسعة الواجهات المحددة في خطة التطبيق، ضمن نمط المعاملات والطبقات المعتمد.

وُثق قرار مستقل لأن إعادة ترقيم الملفات توازن إزالة أثر العدّاد العام مع حفظ المراجع السابقة، ويصعب عكسها بعد عودة العمل.

## الجولة الثالثة — محسومة

- الانتقال أثناء توقف قصير للكتابة، مع نسخة احتياطية وكشف تحويل والتحقق قبل إعادة فتح التطبيق.
- إجراء فردي داخل شاشة المرضى لمدير العيادة: إدخال القديم وإظهار الاسم والجديد ورابط الملف؛ لا جدول شامل أو تصدير.
- الاحتفاظ بالسجل ما دام ملف المريض موجودًا، دون حذف تلقائي أو انتهاء زمني.

## الاعتماد النهائي — مكتمل

اكتملت قرارات المجال الإحدى عشرة. أعدت [خطة التطبيق](proposal.md) السلوك والعقود والملكية والمعاملة والانتقال والتحقق، مع [قرار معتمد](../../docs/adr/0003-clinic-local-patient-numbering.md). اعتمد المستخدم صراحةً الخطة المعروضة، بما فيها توسيع واجهة عمليات المرضى وربطها بنطاق إنشاء العيادة؛ لا استثناء أو تغيير لمدير المعاملات العام.

قال المستخدم «تم الاعتماد» بعد عرض السؤال النهائي وخيار التوثيق فقط أو بدء التنفيذ. لم يحدد بدء التنفيذ؛ ثُبت الاعتماد واكتملت المقابلة دون تعديل كود أو بيانات. لا أسئلة قرار معلقة. عند التكليف بالتنفيذ تُتبع الخطة المعتمدة، وأي خروج عنها يعود للمستخدم.

تفضيل المستخدم: الأسئلة في نوافذ وبالعربية فقط دون مزج المصطلحات الأجنبية. الاقتراحات ليست قرارات ما لم يخترها المستخدم.
