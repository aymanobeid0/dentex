# خطة فصل ترقيم ملفات المرضى — معتمدة للتطبيق

التاريخ:2026-11-04. المصدر [إجابات المقابلة](design.md). اعتمد المستخدم هذه الخطة والتوسعة المحددة بقوله «تم الاعتماد» في2026-11-04. التنفيذ لم يبدأ، والمخطط الحالي لم يتغير.

## السلوك الذي اختاره المستخدم

- لكل عيادة تسلسل أرقام مستقل. البداية١ افتراضيًا، ويختار مدير البرنامج بداية أخرى عند إنشاء العيادة. واجهة الضبط ضمن إنشاء العيادة فقط؛ لا عملية لتعديل أرقام أفراد أو إعادة ضبط التسلسل بعد أول مريض.
- يعاد ترقيم المرضى الموجودين مرة واحدة: يبدأ كل نطاق عيادة من١، بحسب الرقم القديم تصاعديًا. تبقى معرّفات الملفات وروابطها وحقولها الأخرى، والحسابات والعيادات والصلاحيات، كما هي.
- بعد الانتقال الرقم فريد ومتزايد داخل العيادة، دون اشتراط انعدام الفجوات، ولا يعاد استخدامه بعد الأرشفة أو تصفيره سنويًا. تخصيص البداية يقبل عددًا صحيحًا موجبًا ضمن سعة تخزين أرقام الملفات؛ لا بادئات أو صيغة سنوية جديدة.
- يبقى البحث المعتاد بالجديد فقط. مدير العيادة وحده يدخل رقمًا قديمًا في إجراء خاص بشاشة المرضى، فيرى اسم المريض ورقمه الجديد ورابط ملفه. لا قائمة شاملة أو تصدير أو إتاحة للطبيب والاستقبال أو مدير البرنامج. يُحفظ السجل ما دام الملف موجودًا دون حذف زمني.
- أرقام الفواتير مستقلة لكل عيادة عند تنفيذ الفواتير لاحقًا؛ لا تنفيذ فواتير أو عدّاد تجاري شامل في هذه المرحلة.

## التغيير المحدد المعتمد

القاعدة الحالية للتواصل بين الوحدات تمنع وصول موديول إلى repository موديول آخر، وتلزم ربط العمليات الممتدة بمعاملة واحدة. المطلوب توسيع الواجهات المعلنة وفق النمط الموجود، دون استثناء أو تخفيف فحص:

1. يملك موديول المرضى جدول عدّاد لكل عيادة وجدول سجل التحويل. لا يملك موديول العيادات الكتابة المباشرة لهما.
2. تضاف عملية معلنة لتهيئة ترقيم المرضى، ويستدعيها إنشاء العيادة من خلال نطاق المعاملة الحالي. تربط طبقة تجهيز التطبيق عمليات المرضى بنفس عميل المعاملة الذي ينشئ العيادة والأدوار والمدير. فشل أي خطوة يرجع الجميع معًا.
3. يبقى توليد الرقم وإدخال المريض داخل معاملة التسجيل الواحدة. تحدث repository المرضى صف العدّاد الخاص بالعيادة ذريًا ثم تدخل الملف؛ لا حساب أكبر رقم عند كل تسجيل أو قفل عام يجمع العيادات.
4. تضاف قراءة فردية لسجل التحويل داخل موديول المرضى بطبقات route/controller/service/repository الحالية، مع تحقق مدير العيادة الحالي وعزل عيادة الجلسة.

التفاصيل التقنية للواجهة المقترحة، مفصولة عن النص العربي:

```text
patients/index.ts
  PatientsOperations.initializeNumbering(clinicId, start): Promise<void>

ClinicsScope
  patients: PatientsOperations

POST /api/clinics
  patientFileNumberStart?: string
  default: "1"; positive decimal integer; maximum: 9223372036854775807

GET /api/clinic/patients/numbering-history/:oldFileNumber
  clinic admin only; clinicId from session
  200: { id, name, fileNumber }
  400: invalid_input; 401: unauthorized; 403: forbidden; 404: not_found
```

لا يضاف معرّف عيادة إلى مدخلات تسجيل المريض أو بحث السجل. يبقى رقم الملف نصًا في التبادل لحفظ دقة الأرقام الكبيرة. عند بلوغ نهاية سعة الأرقام يرفض التسجيل بخطأ معروف دون رقم مكرر أو التفاف العدّاد؛ تبقى المسودة. لا تكرار تلقائي للكتابة.

العداد المقترح يحتفظ بنقطة البداية وآخر رقم مخصص، ويبدأ آخر رقم قبل البداية بواحد. تحديثه مشروط بعدم تجاوز السعة. قيد التفرد الحالي لرقم الملف داخل العيادة باقٍ؛ يضاف قيد يربط سجل التحويل بمعرّف المريض وعيادته معًا. سجل التحويل يربط القديم بمعرّف المريض الثابت، وتقرأ النتيجة الرقم الجديد من الملف؛ لا مزامنة لنسختين من رقم الملف.

الأثر: عقود إنشاء العيادة وعمليات المرضى المعلنة ونطاق إنشاء العيادة وتجهيزها ستتوسع، مع ترحيل بيانات وجداول تخص المرضى. لا تغيير في TransactionManager العام أو اتجاه الاعتماديات، ولا كشف Prisma لقواعد العمل. البديل المطابق لكن الأقل تنسيقًا هو التهيئة الكسولة عند أول تسجيل؛ لا يثبت إعداد البداية ذريًا مع إنشاء العيادة، لذلك التوصية الربط بالمعاملة القائمة. حصلت الموافقة المحددة على هذه التوسعة ضمن اعتماد الخطة؛ أي توسعة أخرى تحتاج قرارًا مستقلًا.

## الانتقال الآمن

1. معاينة عدد الملفات وخطة القديم إلى الجديد لكل عيادة للقراءة فقط. يحفظ الكشف والنسخ خارج Git وبوصول محلي محدود؛ لا بيانات مرضى في المواصفات أو مخرجات المحادثة.
2. نافذة صيانة توقف جميع عمليات الكتابة ذات الصلة وكل نسخ التطبيق التي تتصل بالقاعدة. تؤخذ النسخة الاحتياطية النهائية ويولد الكشف النهائي بعد توقف الكتابة وقبل أي تغيير، حتى لا تضيع تسجيلات بين المعاينة والتنفيذ.
3. يتحقق من قابلية الاسترجاع في بيئة معزولة. لا reset لقاعدة التطوير أو حذف volume أو تهيئة حسابات. عند تعذر النسخ أو التحقق يتوقف الانتقال.
4. ترحيل واحد ذري يحفظ خريطة كل ملف قائم ثم يعيد الترقيم لكل عيادة ويهيئ عدادها. يعالج تعارضات القيد أثناء إعادة الترقيم على مرحلتين داخل المعاملة، دون إظهار أرقام وسيطة للمستخدمين. يلغى مولّد الأرقام العام؛ الإصدار القديم لا يخصص أرقامًا مشتركة عند الرجوع للعمل.
5. التحقق قبل فتح التطبيق: أعداد العيادات والملفات ثابتة، ومعرّفات المرضى وحقولهم الأخرى محفوظة، ولكل ملف سابق سجل تحويل صحيح، والأرقام الجديدة تطابق كشف الترتيب، والعداد التالي مستقل وصحيح لكل عيادة. يشمل ذلك العيادات الخالية من المرضى.
6. تشغيل النسخة الجديدة فقط، وإعادة تحميل واجهات المستخدم لإزالة ذاكرة الأرقام السابقة. التراجع قبل استئناف الكتابة يستند إلى النسخة الموثقة؛ بعد عودة تسجيلات جديدة لا تستعاد نسخة قديمة تلقائيًا بما يحذفها، بل يلزم تصحيح يحفظ السجلات الجديدة.

لا يوقف الوكيل خدمة أو يغير بيانات أثناء هذه المقابلة. تطبيق الترحيل على التطوير يكون ضمن التنفيذ المعتمد؛ النشر في البيئات الأخرى يبقى يدويًا وفق دليل النشر.

## الواجهة والتحقق

حقل البداية في إنشاء العيادة، وإجراء البحث الفردي القديم داخل شاشة المرضى، بالعربية والفرنسية وبالاتجاهين وبمكونات Radix المناسبة منclient/ui، دون إعادة تصميم. Query يملك القراءة والحفظ وفق سياسة المشروع، والمسودات محلية؛ يعاد التحقق من الصلاحية، ولا تظهر نتائج محفوظة بعد سحب صلاحية المدير.

اختبارات عند UI وHTTP والترحيل علىdentex_test معزولة: بداية افتراضية ومخصصة لعيادتين، عدم تأثر عداد بنشاط الأخرى، التسجيل المتزامن، رجوع تهيئة العدّاد مع معاملة إنشاء العيادة عند فشل متأخر، وإعادة ترقيم بيانات مصطنعة وخريطة كاملة وثبات UUID والحقول. تختبر القيم غير الصالحة ونهاية السعة، والبحث الجديد عند تطابقه مع رقم قديم لمريض آخر، وعزل سجل التحويل ورفض غير المدير وإخفاء الرد المتأخر بعد سحب صلاحياته.

الأنواع والاختبارات المستهدفة ثم المجموعة الكاملة والبناء وفحصا المعمارية ومراجعة main مجلوب حديثًا تشمل الملفات الجديدة. لا تضاف طريقة اختبار أو استثناء معماري لتجاوز القواعد. بعد التنفيذ يترك التطبيق وبيئة التطوير للفحص المحلي قبل أي PR وفق تعليمات المشروع.
