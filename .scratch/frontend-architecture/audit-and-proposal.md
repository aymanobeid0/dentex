التقصير في المراجعة السابقة: قُيّمت الوظائف والاختبارات والتوافق مع القواعد الموثقة، ولم يُقيّم غياب هيكل واجهة واضح. مراجعة retro للوثائق لا تكفي لإثبات جودة تنظيم الكود. نتائج الاختبارات تبقى دليل السلوك الذي اختبرته، والقرار المعتمد لإدارة الحالة يبقى نافذًا.

## الهيكل المقترح

```text
client/
  entry.tsx
  app/
    App.tsx
    AppProviders.tsx
    navigation.ts
    layout/
      AppShell.tsx
      AppSidebar.tsx
  features/
    auth/
    clinics/
    employees/
    roles/
    account/
    patients/
  shared/
    api/
    query/
    i18n/
    styles/
  ui/                         # مسار Radix المعتمد يبقى كما هو
```

داخل كل feature نضيف ما تحتاجه فعلًا. مثال المرضى:

```text
patients/
  index.ts                    # interface عامة مختارة
  pages/PatientsPage.tsx       # تركيب تدفق الميزة
  components/                 # القائمة والملف ونموذج التسجيل
  hooks/usePatientSearch.ts   # تنسيق تفاعل البحث
  queries.ts                  # query hooks والمفاتيح
  api.ts                      # عمليات HTTP
  types.ts                    # عقود الميزة
```

المقترح تنظيم بحسب الميزة، مع تركيب تطبيق وبنية مشتركة محدودين. لا يفرض طبقات route/controller/repository الخاصة بالخادم على React. الهدف Module تخفي تفاصيلها خلف interface صغيرة وتجمع معرفة التغيير في مكان واحد.

## قواعد الملكية والاعتماديات

1. app يركب providers والتخطيط والتنقل وشاشات الميزات؛ عمليات CRUD وطلبات HTTP تملكها الميزات.
2. كل feature تملك شاشاتها ونماذجها وعقودها وعملياتها وhooks وquery keys. مكونات العرض تستعمل interface الميزة بدل بناء fetch مباشرة.
3. shared/api للنقل والأخطاء والإلغاء والعزل العام. shared/query لبناء العميل ونطاق المفاتيح وسياسة القراءة وإشارات المتصفح. لا DTO مرضى/موظفين أو بيانات API في Context عام.
4. features/auth تملك Account وهوية الجلسة والدخول والخروج. تمد البنية المشتركة بالنطاق والنقل؛ تعتمد الميزات الأخرى على البنية العامة دون استيراد ملفات المصادقة الداخلية.
5. اتجاه الاعتماد: app → features → shared/ui. لا تستورد shared أو ui من app/features. لا استيراد مباشر بين داخليات ميزتين؛ ينسق app التدفق عبر واجهاتهما أو callbacks القائمة.
6. index.ts لكل feature يعلن الصادرات المطلوبة فقط. الاستيراد الخارجي عبره، والداخلي صريح. تُمنع الدورات والوصول إلى الملفات الداخلية عبر فحص اعتماديات فعلي.
7. اسم ملف المكون يطابق اسمه، والـhook يبدأ use. تنسيق TSX مقروء، وفصل الملف عند تعدد مسؤولياته؛ لا حد أسطر اعتباطي أو مجلدات فارغة استباقية.
8. يبقى ui في client/ui وفق قرار Radix. تبقى ترجمتا AR/FR وتفضيل dentex-lang والتصميم والسلوك المعتمدان.
9. تُطبق قواعد Vercel ذات الصلة: ملكية الحالة قرب مستهلكها، ثبات هوية المكونات، اعتماديات effects الصحيحة، مشاركة الاشتراكات، وتقييم التحميل والحزم. الواجهة العامة للميزة تقتصر على صادرات واضحة؛ تُراجع آثار إعادة التصدير على الحزمة. تبقى TanStack Query وReact/Vite وفق قرارات المشروع، وتُقاس التحسينات المناسبة لهما.

## التنفيذ بعد الموافقة

1. تسجيل موافقة المستخدم والهيكل في وثيقة معمارية واجهة مستقلة، وربطها بالمراجع المعتمدة دون تغيير معمارية الخادم.
2. نقل الملفات وفصل مسؤوليات App والشاشات فعليًا؛ نقل الملفات الكبيرة إلى مجلدات وحده لا يحقق المطلوب.
3. تنظيم اختبارات الواجهة ومساعداتها تحت tests/client بحسب الميزة عند الحاجة، مع حفظ نقاط UI/HTTP المعتمدة.
4. إضافة فحص اعتماديات واجهة مستقل إلى CI مع أمثلة رفض وقبول؛ يبقى فحص الخادم دون تخفيف.
5. فحص الأنواع والاختبارات المستهدفة أثناء النقل، ثم كامل الاختبارات والبناء والمعمارية والتحقق في المتصفح باللغتين والاتجاهين ولوحة المفاتيح، مع الجلسة والانقطاع والبحث. خط الأساس الحالي 155 اختبارًا.
6. مراجعة مقابل main مجلوب حديثًا، وإبقاء البيئة الدائمة لفحص المستخدم قبل PR. لا يبدأ تنفيذ03–09 ضمن إعادة التنظيم؛ استخراج تدفق قائم لا يغير عقده أو يرحله وظيفيًا إلى Query قبل تذكرته.

## الأثر والمخاطر والبديل

الملفات المتأثرة: client واستيرادات اختبارات الواجهة وفحص الاعتماديات. المخاطر: ترتيب providers وعمر QueryClient وإلغاء الجلسة وتنقل hash وتركيز الحقول وترتيب CSS. تُحفظ العقود والصلاحيات واللغات والتصميم وقاعدة التطوير وحساباتها، وتُثبت عبر الاختبارات والمتصفح.

البديل هو إبقاء الجذر المسطح وتحسين قراءة الملفات موضعيًا. يقلل تغيير الاستيرادات لكنه يبقي ملكية الميزات وفحص اعتماديات الواجهة غير محددين؛ لذلك أوصي بالمقترح أعلاه.
